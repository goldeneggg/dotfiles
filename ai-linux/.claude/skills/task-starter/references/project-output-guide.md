# ドキュメント生成ガイド

Phase 3 の生成前に全文読む。本文の判断基準は [SKILL.md](../SKILL.md) に従う。

各ドキュメントは `templates/*.md` のテンプレートをベースに生成する。**HTML を選んだ場合は、テンプレートの構造を `html-output-guide.md` のルールに従って自己完結HTMLに変換して書き出す**（共有シェル `templates/html-shell.html` を使用、Mermaid は `<pre class="mermaid">`、TODOの依存メタは `<script type="application/x-task-meta">` に埋め込む）。必要な情報と保存形式は維持し、任意節は対象に合わせて調整する。

`../../_shared/references/document-writing-guide.md` を読み、文書ごとの役割と書き方を適用する。詳細の生成後にルートREADMEを仕上げ、計画全体を説明する。

1. **references/ - 現状分析（既存コード改修時のみ）**
   - `templates/reference-template.md` をベースに作成
   - 調査の結論を先に述べ、確認した事実・根拠・影響・未確認事項を分ける。構成や処理フローは課題の理解に必要な範囲に絞る
   - ユーザーへ確認する前に[確認の提示形式](user-confirmation-guide.md)を全文読む
   - 不明点は「ユーザー確認の提示形式」に従って随時確認

2. **specs/ - 仕様書**
   - `templates/spec-template.md` をベースに作成
   - 期待する動作・結果、実現方法と採用理由、制約を記載する。UI/API/データ形式等の詳細は対象に応じて追加する
   - 初回の成功条件と将来の改善候補を分け、候補の扱いは「追加作業の採否」に従う
   - **非機能要件には「開発原則」（セキュリティ・耐障害性・高可用性・スケーラビリティ）の方針を必ず記載**。プロジェクト特性上 N/A の原則は理由を添えて明記する
   - **「完了条件 / 成功の定義」は、期待する動作・結果と確認方法の組で書く**。実環境での確認や人の判断も、必要なら実施時点とともに残す。AIの評価方式に合わせて本来の成功条件を変更しない
   - 条件が曖昧なら、何を見て達成と判断するかを具体化する。自動実行用の指示は Phase 4 のロードマップへ分離する

3. **todos/ - タスク分割（依存メタ付き）**
   - `templates/todo-template.md` をベースに作成
   - TODO化する前に「追加作業の採否」を確認する
   - 「タスクの目的」「作業内容」「受け入れ条件」を先に配置し、対象ファイルや並行作業等の詳細は後方の「実行メモ」にまとめる。重要な前提・制約は該当作業・条件の近くにも残す
   - 「TODOタスク分割ガイドライン」に従い、利用できる成果と担当のまとまりで分割する。各タスクは受け入れ条件を満たし、エラー無しでコミット可能な範囲にする
   - **連番フォルダは `0xx` 番台**で付与: `001-setup/`, `002-implement-xxx/`, ...（`1xx` 番台は実行中の追加タスク用に予約。「TODOタスク番号規約」参照）
   - **各 `README.md` 冒頭にYAMLフロントマターで以下を必ず明記**:
     - `id`: タスクID
     - `estimated_time`: 推定時間
     - `depends_on`: 前提タスクIDの配列（無ければ `[]`）
     - `parallel_group`: 同時に行う作業が分かるグループ名（無ければ `null`）
     - `parallelizable`: subagentで並行実行を推奨するか
   - **各タスクで4原則を点検**し、「開発原則」に従って対策の要否と分割を判断する。検討結果は「実行メモ」内の「開発原則チェック」に記載する
   - 各TODOの「タスクの目的」に「必要な理由」「解決する課題」「ユーザーから見た変化」を必ず記載する。プロジェクト全体の説明をそのまま使い回さず、そのタスクを実施する理由と効果が分かる固有の文章にする。「必要な理由」には、この作業を行わなければ満たせない初回の成功条件と、未達になる理由を示す
   - 内部作業で画面や操作が直接変わらない場合は、その事実を明記した上で、品質・安全性・障害低減・保守性などを通じて利用者に届く間接的な変化を説明する。単に `N/A` としない
   - 作業項目には `W-01`、受け入れ条件には `AC-01` のようなタスク内で一意かつ安定したIDを付ける。TODOには進捗を表すチェックボックスを置かない
   - 各TODOの生成時に同じIDの `progresses/{ID}/PROGRESS.md` と `logs/{ID}/` を作成する。`PROGRESS.md` は共有契約のテンプレートを使用し、「タスクの目的」へTODOと同じ3項目を転記する。状態を `未着手`、残作業を全 `W-ID`、受け入れ条件の検証を全 `AC-ID: 未確認`、その他の空項目を `なし` で初期化する。受け入れ条件の本文は転記しない
   - 全TODOと個別 `PROGRESS.md` の生成後、`python3 ~/.claude/skills/_shared/scripts/sync_progress_index.py "{project_root}"` を実行し、`progresses/README.md` に全タスクをID昇順で反映する。個別正本を一覧から上書きしない
   - ユーザーへ確認する前に[確認の提示形式](user-confirmation-guide.md)を全文読む
   - 不明点は「ユーザー確認の提示形式」に従って随時確認

4. **ルートREADME - 全体説明**
   - `init_project.py` の雛形を、収集した要件と生成した詳細文書で埋める。Why・What・How、範囲、完了の判断、重要な未決事項を説明する
   - 「どう進めるか」は細かなTODOを意味のある段階にまとめ、各段階の必要性・成果と対応するTODOへのリンクを示す。全件の明細はロードマップに任せる
   - 詳細の説明先と進捗一覧へ案内する。概要説明用の別文書は通常追加しない
