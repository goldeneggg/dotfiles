# QA計画の書き方

読み手は変更の実装を知らないQA担当者とする。コードの関数名や差分行から操作方法を推測させず、利用者の言葉で目的・操作・期待結果を書く。技術用語は操作に必要なものだけ使い、初出で短く説明する。

## 計画の構成

以下を土台とし、不要な項目は省く。ただし `QA-00` は必須とし、修正の成否を判断するうえで最も重要かつ欠かせないシナリオを先頭に置く。準備はその前に独立して書き、補足ケースは `QA-01` 以降に続ける。ケース数を固定せず、変更点とリスクに合わせる。表に長い操作手順を詰め込まず、ケースごとに番号付きで書く。

```markdown
## QA計画

- 対象: {PR URL、タイトル、head SHA}
- 状態: 未実行
- 変更の要点: {誰の、どの操作が、どう変わるか}
- 確認範囲: {変更の中心と直接影響する既存動作}
- 対象外: {あれば範囲と理由}

### 準備

- 環境: {URLまたは起動方法、対象版の確認方法、必要なOS等}
- アカウント: {必要な権限、入手方法、利用可否。秘密情報は記載しない}
- データ・ファイル・HTMLページ: {所在・確認状況、入手または作成手順、準備完了の確認方法}
- 使用ツール: {方法と選択理由、エージェントで実行可能か・人の操作が必要か}
- 未確定事項: {不足情報、影響するケースID。なければ省略}

### QA-00: {修正内容に対して最も重要かつ欠かせないシナリオ}

- 目的・根拠: {対応する変更点・受け入れ条件と参照先}
- 優先度: 最優先・必須。{このシナリオを選んだ理由}
- 使用ツール: {共通の準備と異なる場合に記載}
- 前提: {開始画面、ログイン状態、データ、先行ケース等}

操作と期待結果:

1. {操作対象と具体的な入力・操作}。
   - 期待結果: {表示、出力、保存状態など、読み手がその場で判定できる内容}。
2. {次の操作}。
   - 期待結果: {必要なら再読込後の状態や、変化しない既存データも確認}。

後片付け: {作成したデータ等の戻し方。不要なら「不要」}

### QA-01: {補足する確認内容}

{QA-00と同じ構成で、目的・根拠、優先度と理由、前提、操作と期待結果、後片付けを書く。以後も必要なケースを続ける}
```

## データ・HTMLページの準備

- 各ケースが使うデータ・ファイル・ページについて、対象版のリポジトリや手順書から所在と利用条件を確認する。資料上の存在と実環境での利用可否を区別し、未確認なら実行前の確認方法を記載する。「該当データがある状態」「テストページを開く」だけで済ませない。
- 利用できる既存のサンプル・データ投入手順・アプリの作成機能を優先する。ない場合は、検証に必要な最小のデータやHTMLを用意できるよう、入力値・ファイルの全文・作成コマンドなどを計画に含める。作業場所、保存名、実行順、準備完了時に確認できる件数・内容・表示も示す。入力値を検証用に設計することと、実在するIDや所在を捏造することを混同しない。
- HTMLページが必要なら、既存ページのURL・起動方法を示すか、必要な要素を含む自己完結したHTMLと保存・表示方法を示す。HTTP配信、アクセス先の制約、別ファイルなどが必要なら、その準備まで含める。別の画像やデータを参照するだけで、それらの用意を省略しない。
- 用意したデータ・ページで実際の検証対象が動き、元の不具合や受け入れ条件を確認できることを確かめる。アプリ本体・認証・通信が必要なシナリオを、見た目だけのHTMLで代用しない。
- 情報・権限が足りず準備を具体化できない場合は、不足するもの、分かっている入手先・依頼先、影響するケースIDを示す。「適宜用意する」と読者に補完を任せず、該当ケースの実行可否は未確定とする。`--exec` でも揃わなければ `BLOCKED` とし、推測のデータやページで合格判定しない。

## 再現できる粒度

- 「正常に動く」「適切に表示される」「エラーにならない」だけを合格条件にしない。何がどこに表示されるか、何が保存されるか、何が変わらないかを具体化する。正確な文言が仕様で決まっていない場合、文言を捏造せず確認すべき意味を書く。
- UIは開始画面への入り方、項目名・ボタン名、入力値、確認位置を書く。CLIは作業ディレクトリ、準備するファイル、コマンド、標準出力・標準エラー・終了コード・生成物のうち判定に必要なものを書く。APIはメソッド・パス・入力・認証の設定方法と、応答・副作用の期待を示す。
- 未確定の接続先やデータIDは、その値の入手・設定が必要であると明記する。推測の値で実行できるように見せない。人による準備や判断が必要なケースも、判明している手順は残す。
- バグ修正では報告された条件を再現手順へ落とし込む。正常系を一度試すだけで、元の不具合を確認したことにしない。
- ビルドや自動テストを含める場合、何を確認できるかと結果の見方を併記する。QA担当者が使う導線の確認を、説明なくテストコマンドだけに置き換えない。

## 書き方の例

ブラウザ拡張の仕様が「ページ内のh2見出しを抽出する」、修正内容が「見出し内の強調部分が欠落する不具合」と確認できた場合。以下は対象版の拡張が導入済みで、ローカルHTTPページへのアクセスが許可され、Python 3を利用できる環境での例。実際の計画では、その導入・権限設定もプロジェクトの手順で具体化する。

### 準備: 存在しない検証用ページを作る

1. 作業用フォルダ `qa-heading` を新規作成し、その中に次の全文を `heading.html` としてUTF-8で保存する。別の画像やデータファイルは不要。

   ```html
   <!doctype html>
   <html lang="ja">
   <meta charset="UTF-8">
   <title>見出し抽出の確認</title>
   <h2>配送先の<strong>変更</strong></h2>
   </html>
   ```

2. ターミナルで `qa-heading` フォルダへ移動し、次を実行する。起動したターミナルはそのままにする。

   ```sh
   python3 -m http.server 8000 --bind 127.0.0.1
   ```

3. 対象ブラウザで `http://127.0.0.1:8000/heading.html` を開く。「配送先の変更」が見出しとして表示され、「変更」が太字になっていることを確認する。これを準備完了の条件とする。

### QA-00: 見出しの強調部分も欠落せずに抽出される

- 目的・根拠: 修正対象の不具合が起きるHTML構造で、抽出結果を確認する。
- 優先度: 最優先・必須。元の症状を直接検証できるため。
- 前提: 上記のページ準備が完了し、対象版の拡張を利用できる。

1. `http://127.0.0.1:8000/heading.html` を開いた状態で拡張の操作画面を開き、「見出しを抽出」を押す。
   - 期待結果: 結果一覧に「配送先の変更」が1件表示され、「変更」の文字が欠落しない。

後片付け: ページを閉じ、サーバーを起動したターミナルでCtrl+Cを押す。今回作成した `qa-heading` フォルダを削除する。

この例の機能名・操作名・URL条件を他のPRへ流用せず、調査した事実で置き換える。

## 実行結果の記録

結果は計画と同じケースIDで対応付ける。期待結果を実際の結果欄へそのまま転記せず、観測した値や状態を書く。

| ID | 判定 | 実際の結果・証跡 | 残作業 |
|---|---|---|---|
| QA-00 | PASS / FAIL / BLOCKED / NOT RUN | 最重要シナリオの実測結果、または判定できない理由 | 再実行に必要な条件等 |
| QA-01 | PASS / FAIL / BLOCKED / NOT RUN | 観測した画面・値・応答、または判定できない理由 | 再実行に必要な条件等 |

不具合はケースID、再現手順、期待結果と実際の結果、利用者への影響をまとめる。仕様の未確定や環境準備の失敗と、製品の不具合を区別する。
