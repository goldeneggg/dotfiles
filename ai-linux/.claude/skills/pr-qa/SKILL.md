# PR QA

実装を知らないQA担当者が、何を準備し、どこで何を操作し、どの結果なら合格か判断できる手順を日本語で作る。

## 呼び出し

```text
$pr-qa <PR URL | #番号> [--exec] [--output <pr-desc|pr-comment>]
```

- 対象PRは1つ。URL指定ではそのリポジトリを使う。`#番号` は現在のリポジトリから解決し、リポジトリを特定できない場合だけ確認する。
- `--exec`: 作成した計画を提示し、出力指定があれば出力した後にQAを実行する。未指定なら情報収集と計画作成だけを行い、アプリ起動・テスト・QA操作は実行しない。
- `--output pr-desc`: 計画を既存のPR説明欄の末尾に追記する。
- `--output pr-comment`: 計画を通常のPRコメントとして1件投稿する。Reviewの提出ではない。
- `--output` 未指定なら計画はチャットにだけ表示する。出力先の併用、任意ファイルパス、未知のオプション、値の欠落は入力エラーとして示し、外部操作前に訂正を求める。

`--output` は指定先への計画の公開、`--exec` は対象のQA実行の指示として扱い、同じ操作の許可を再確認しない。実行結果はチャットで報告し、結果の外部投稿・追記は別途指示がある場合だけ行う。

## 1. PRと期待動作を理解する

1. 利用可能なGitHub連携ツールまたは `gh` で、対象のリポジトリ、PR番号、URL、状態、タイトル、説明、base/headのブランチとSHA、変更ファイル一覧・差分を取得する。以後の取得・投稿では対象リポジトリとPRを明示し、現在ブランチのPRと取り違えない。
2. 関連Issue・受け入れ条件・仕様と、目的の理解に必要なPR内の議論を読む。PRの説明と差分を照合し、「誰の、どの操作が、どう変わるか」を整理する。バグ修正なら発生条件、修正前の症状、修正後の期待動作を特定する。
3. 対象版の関連コード・既存テスト、適用される `AGENTS.md`、README等の起動・検証手順、CI設定を必要な範囲で読む。大きな差分はファイルごとに分け、未取得・未確認の範囲を残す。ローカルの現在のファイルをPR head版とみなさない。
4. 仕様と実装が食い違う場合、実装に合わせて合格条件を書き換えない。仕様がない部分の推測は仮定と明記し、合否に影響する曖昧さは確認事項にする。判明した範囲の計画は先に作る。

計画には対象PRと調査時点のhead SHAを記録する。差分取得が不完全な場合は、対象範囲を明示した暫定計画とし、PR全体を網羅したと扱わない。

## 2. 検証方法とツールを選ぶ

変更ファイルの拡張子だけで決めず、利用者が変更を体験する入口、公開された契約、既存の検証方法から選ぶ。複数の入口に影響する変更では必要な方法を組み合わせる。

| 変更と観測したい動作 | 主な検証方法 | 確認する前提 |
|---|---|---|
| Web画面、入力、画面遷移、表示 | ブラウザ操作、既存の画面テスト | 対象版のURL、ログイン権限、対象ブラウザ・表示サイズ |
| CLI、スクリプト、ファイル入出力 | ターミナルで実際のコマンドを実行 | 作業ディレクトリ、実行環境、入力データ、出力先、終了コード |
| API、バックエンドの応答 | APIクライアント、既存の結合テスト | 接続先、認証方法、リクエスト、応答と保存状態 |
| ライブラリ、内部処理、設定、ビルド | 既存テスト、利用側の最小の実行例、設定の読込・ビルド確認 | 対象バージョン、呼出し元、設定の適用方法 |
| デスクトップアプリ、拡張機能、端末固有の機能 | 対象アプリ・実機の操作 | インストール済みの版、OS、権限、必要な機器 |
| 文書のみ | 記載手順・リンク・実際の画面やコマンドとの照合 | 読者、前提環境、記載内容に対応する版 |

ケースごとに選択理由を短く示す。既存の自動テストで確認できる範囲を利用し、画面や操作感など別の観測が必要な部分を補う。CI成功やコードの読解だけで、未操作の動作を検証済みにしない。

検証に適した方法と、このセッションで操作可能なツールを区別する。利用可能な連携ツール・ブラウザ・ターミナル等を確認し、実際に使うツールに適用される利用手順を読む。ツールがない、対象URL・起動方法が分からない、実機が必要などの場合は、手動手順と不足条件を残す。別の方法で同じ確認ができると勝手に扱わない。

## 3. QA計画を作る

計画作成時に [references/qa-plan.md](references/qa-plan.md) を読み、第三者が再現できる粒度で書く。

- 最初のケースを必ず `QA-00` とし、修正内容に対して最も重要かつ欠かせないシナリオを記載する。バグ修正なら元の発生条件で修正を確かめるシナリオ、機能追加なら中心となる受け入れ条件を選び、選定理由を示す。準備作業だけを `QA-00` にしない。
- 補足のケースは `QA-01` 以降に置き、`QA-00` と同じ確認を重複させない。直接影響する既存動作の回帰を優先し、境界値・異常系・権限差・互換性は変更との関係を説明できるものだけ含める。
- ケースにはID、確認目的、優先度、前提・データ、番号付き操作、観測可能な期待結果、必要な後片付けを含める。ケース間の依存がある場合は実行順を示す。
- 画面名・ボタン名・入力値・保存先などを具体化する。CLI/APIではそのまま使えるコマンドやリクエストに加え、実行場所と結果の読み方を書く。未確認のURL・アカウント・データを既存のものとして扱わず、検証用に新規作成するものと区別する。
- 各ケースを変更点や受け入れ条件と対応付ける。対象外とする確認には理由を示し、実行できないケースを計画から消さない。全機能の網羅テストへ広げない。

各ケースに必要なデータ・ファイル・HTMLページを洗い出し、所在と利用条件を調べる。存在を未確認のまま前提にせず、既存のものの入手先・確認方法、または存在しない状態からの具体的な作成手順と準備完了の確認方法を、ケースより前に書く。用意する方法が分からないものは不足条件と影響するケースを示す。詳細は参照文書の「データ・HTMLページの準備」に従う。

完成した計画をチャットで提示する。`--exec` がない場合は準備手順・必要なファイル内容の提示までとし、データ投入やページの起動は行わない。`--exec` があっても、実行前の計画を結果として書かない。

## 4. 指定先へ計画を出力する

`--output` がある場合だけ実施する。計画は「未実行」と明記し、対象PR、head SHA、前提条件、未確定事項を含め、過去のチャットを読まなくても使える本文にする。認証情報・個人情報・ローカルにしか通じないパスを公開しない。

1. 投稿直前にPRのhead SHAを照合する。調査後に更新されていたら変更を読み直し、計画と対象SHAを揃えてから出力する。
2. `pr-desc` では最新の説明欄を再取得し、その全文を保持した末尾に区切りを入れ、`## QA計画` から始まる計画を追記する。既存の説明・チェックボックス・他者の追記を置換しない。`pr-comment` では `## QA計画` を含む通常コメントを1件投稿する。同じhead SHA・同じ計画が既に指定先にあれば重複投稿せず、その場所を報告する。
3. 本文は構造化されたツール引数で渡す。`gh` を使う場合はセッション固有の一時ファイルに本文を書き、`gh pr edit` または `gh pr comment` の `--body-file` と明示した `--repo`・PR番号で送る。本文をシェルの文字列連結で組み立てない。
4. 反映後の本文・コメントを確認し、投稿先URLと成否を記録する。成否不明なら最新の投稿先を調べ、確認できるまで再送しない。出力失敗時も計画をチャットに残し、別の投稿先へ無断で切り替えない。

## 5. QAを実行する

`--exec` がある場合だけ実施する。出力の成否とQA実行の可否は別に扱い、独立して進められるケースは続行する。

1. 実行対象の版、環境、アカウント、データ、ツールを確定する。ローカルはPR head SHAを照合し、切替が必要ならユーザーの作業ツリーを変更せず、別worktree等で対象版を用意する。配備済み環境はビルド情報等で対象版を確認する。版が確認できない環境の結果を、そのPRの合格根拠にしない。
2. 計画の準備手順を実施し、必要なデータ・ページが意図した状態で利用できることを確認してからケースを実行する。既存のプロジェクト手順を優先し、テスト環境での通常の操作・使い捨てデータや入力用HTMLの作成など、依頼範囲内で元に戻せる準備は進める。本番データの変更・削除、実課金、外部への通知送信など別の影響を伴う操作は、既存の許可がなければその操作の直前に対象・影響を示して確認する。認証や実機操作を人に依頼する場合も、独立したケースは続ける。
3. 計画の順序で実行し、ケースIDごとに実際の結果と証跡を記録する。証跡は必要な画面、実行コマンド、終了コード、応答などに絞り、秘密情報を除く。事前のCI結果は参考情報として今回の実行結果と分ける。
4. 不一致を見つけたら期待結果・実際の結果・再現条件・影響を記録する。原因を確認せずに再試行を繰り返さず、継続がデータ破損等につながる場合は依存ケースを止める。修正実装、自動テストコードの新設、commit・push・mergeはこのスキルの範囲に含めない。QAの入力として使う一時データ・HTMLの用意は準備作業として扱う。
5. 作成したテストデータ・起動プロセス等を計画に沿って後片付けする。残ったものと理由を報告する。実行中に対象版が変わった場合は、ケースごとの実行版を分け、未確認の版へ結果を引き継がない。

## 6. 結果を報告する

- 計画のみの場合: 計画全文、対象PR・head SHA、選んだ検証方法と理由、未確定事項、出力結果を示し、「QA未実行」と明記する。
- 実行した場合: 対象PR・実行版・環境、ケースIDごとの判定・実測結果・証跡、不具合、残作業、後片付け、出力結果を示す。

判定は `PASS`（期待結果を実測で確認）、`FAIL`（期待結果との不一致を観測）、`BLOCKED`（環境・権限・仕様等の不足で判定不能）、`NOT RUN`（未実行）を使う。未実施・判定不能を成功に数えず、残っているケースがあればPR全体のQA完了と報告しない。
