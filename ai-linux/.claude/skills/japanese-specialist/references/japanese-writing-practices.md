## 1. 文体の統一

### 文体の自動判定

添削・検証では、まず対象文書の地の文から文体を判定する:

- 文末の「です」「ます」「ました」「ません」が多数 → **です・ます調**
- 文末の「である」「だ」「た」「ない」（体言止め含む）が多数 → **である調**
- 混在している場合は多数派を基準文体とし、少数派を指摘する

新規作成では、ユーザー指定がなければ文書種別で決める:

| 文書種別 | 既定の文体 |
|---|---|
| README・利用者向けガイド・チュートリアル | です・ます調 |
| 設計書・仕様書・ADR・社内規約 | である調（です・ます調でも可、統一が最優先） |
| 箇条書き・表のセル | 体言止め or である調（地の文と混在可） |

### ルール

- 地の文の中で「です・ます調」と「である調」を混在させない
- 箇条書き・表・見出しは地の文と別文体でよいが、箇条書き同士では統一する
- 見出しは体言止めを基本とする

## 2. 文の構造

### 一文の長さ

- **一文は100文字以下**を目安とする（textlint: sentence-length 相当）
- 超える場合は、接続助詞（〜が、〜ので、〜して）の箇所で分割を検討する

### 読点の数

- **一文の読点（、）は3つまで**（textlint: max-ten 相当）
- 4つ以上必要になる文は、構造が複雑すぎるサイン。文の分割を優先する

### 係り受け

- 修飾語と被修飾語は近づける
- 長い修飾節は文の先頭に置く
- 主語と述語の距離が遠い文は分割する

### 悪い例と改善例

```
悪い: この機能は、設定ファイルを読み込み、値を検証し、環境変数で上書きし、最終的な設定オブジェクトを生成するが、検証に失敗した場合は、デフォルト値が使われる。
良い: この機能は、設定ファイルの読み込み・検証・環境変数による上書きを経て、最終的な設定オブジェクトを生成する。検証に失敗した場合はデフォルト値が使われる。
```

## 3. 表現の正確さ

### 二重否定の禁止

- 「〜ないわけではない」「〜なくはない」→ 肯定形に書き換える（textlint: no-double-negative-ja 相当）

```
悪い: この設定を使えないわけではありません。
良い: この設定は使えます（ただし推奨しません）。
```

### ら抜き言葉の禁止

- 「見れる」「食べれる」「変えれる」→「見られる」「食べられる」「変えられる」（textlint: no-dropping-the-ra 相当）
- 技術文書では受身・可能の曖昧さを避けるため「〜できる」への書き換えも検討する

### 同一助詞の連続

- 同じ助詞（特に「の」「に」「で」）を一文で3回以上連続させない（textlint: no-doubled-joshi 相当）

```
悪い: サーバーの設定のファイルの場所を確認する。
良い: サーバー設定ファイルの場所を確認する。
```

### 逆接・接続詞の連続

- 「〜が、〜が、」と逆接の「が」を一文で繰り返さない
- 同じ接続詞（しかし、また、そして等）を連続する文で使わない（textlint: no-doubled-conjunction 相当）

### 曖昧表現の回避

- 「〜など」「〜等」の乱用を避け、列挙が網羅か例示かを明確にする
- 「基本的に」「原則として」を使う場合は例外条件を明記する
- 主語の省略で動作主体が曖昧になる文は主語を補う（システムがやるのか、ユーザーがやるのか）

## 4. 冗長表現の排除

以下のパターンは簡潔な形へ書き換える（textlint: ja-no-redundant-expression 相当）:

| 冗長 | 簡潔 |
|---|---|
| 〜することができる | 〜できる |
| 〜を行う / 〜を実施する | （動詞化する: 検証を行う → 検証する） |
| 〜という〜 | （不要なら削除: 設定という機能 → 設定機能） |
| 〜のような形で | 〜のように |
| まず最初に | まず / 最初に |
| 〜する必要がある | 〜が必要 / 〜すること（文脈に応じて） |
| 〜になります / 〜となります | 〜です / 〜である（状態変化を伴わない場合） |
| 〜したいと思います | 〜します |

- サ変名詞＋「を行う」は原則動詞化する。ただし目的語が長い場合は許容
- 「こと」「もの」の多用を避ける（一文に「こと」2回以上は書き換え候補）

## 5. 表記ルール

### 全角・半角

- 英数字は半角を使う（例: `Node.js 26`、`3件`）
- 全角英数字（Ａ、１）は使わない
- 感嘆符・疑問符を使う場合は全角（！？）とし、直後に続く文はスペース不要

### 和欧文間のスペース

- 半角英数字と和文の間のスペースは**入れる／入れないをプロジェクトの既存文書に合わせ、文書内で統一**する
- 既存の慣習が不明な場合はスペースなしを既定とする

### 括弧・記号

- 和文中の括弧は全角（）、コード・英文中は半角 ( ) を使う
- 中黒（・）は並列の名詞列挙に使い、長い句の列挙には読点か箇条書きを使う
- 三点リーダーは「……」（2倍）を正式とするが、技術文書では「...」も許容。文書内で統一する

### カタカナ長音

- 語末の長音符号は**JIS Z 8301 旧規定（省略）か内閣告示（付与）のどちらかに統一**する
- 判断に迷う場合は長音付与（サーバー、ユーザー、コンピューター）を既定とする
- 「エントリ／エントリー」など文書内での混在を最優先で検出する

## 6. 漢字の開き

副詞・形式名詞・補助動詞は、ひらがな書き（開く）を基本とする:

| 閉じた表記 | 開いた表記 |
|---|---|
| 事 | こと |
| 物・者（形式名詞） | もの |
| 時（形式名詞） | とき |
| 為 | ため |
| 出来る | できる |
| 下さい（補助動詞） | ください |
| 頂く（補助動詞） | いただく |
| 致します | いたします |
| 更に | さらに |
| 既に | すでに |
| 是非 | ぜひ |
| 但し | ただし |
| 又 / 及び / 並びに | また / および / ならびに |
| 或いは | あるいは |
| 尚 | なお |
| 概ね | おおむね |
| 予め | あらかじめ |
| 全て | すべて（「全部」等の熟語は漢字のまま） |
| 様々 | さまざま |
| 〜して欲しい | 〜してほしい |
| 〜する上で | 〜するうえで |

- 実質的な意味を持つ場合は漢字のまま（「時刻の時」「物品の物」「上下の上」）
- 対象文書がすでに閉じた表記で統一されている場合は、統一性を優先して指摘レベルを下げる

## 7. 表記ゆらぎの統一

同一文書内で以下のゆらぎを検出し、多数派または推奨形へ統一する:

- カタカナ語: サーバ/サーバー、インタフェース/インターフェース/インターフェイス
- 送り仮名: 引数の受け渡し/受渡し、問い合わせ/問合せ
- 漢字/かな: 下さい/ください、出来る/できる
- 英語表記: Github/GitHub、Javascript/JavaScript、node.js/Node.js（公式表記を正とする）
- 数字: 一つ/1つ/ひとつ

固有名詞・製品名は必ず公式表記に合わせる。

## 8. 構成と段落

- 1段落1トピック。段落は3〜5文（技術文書なら2〜4文）を目安とする
- 見出しレベルを飛ばさない（h2の直下にh4を置かない）
- 結論・要点を先に、詳細・根拠を後に書く
- 箇条書きは1項目1内容とし、項目間で文法構造（体言止め/文）をそろえる
- 読者が最初に知るべき前提条件（対象バージョン、環境等）は文書冒頭に置く

## 9. 重大度の定義

添削・検証レポートでは指摘を3段階で分類する:

| 重大度 | 基準 | 例 |
|---|---|---|
| **[重大]** | 意味の誤り・読者の誤解を招く | 誤字脱字、同音異義語の誤用、二重否定、主語の欠落による誤読、係り受けの曖昧さ |
| **[推奨]** | 読みやすさを明確に損なう | 文体混在、100文字超の文、読点4つ以上、冗長表現、ら抜き言葉、助詞の連続 |
| **[軽微]** | 統一・洗練の余地 | 漢字の開き、表記ゆらぎ、和欧文間スペースの不統一、体言止めの混在 |

固有名詞の公式表記違反（GitHub等）は[推奨]とする。
