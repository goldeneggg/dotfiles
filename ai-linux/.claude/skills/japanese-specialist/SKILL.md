# Japanese Specialist

日本語ドキュメントの新規作成・添削・検証を行う専門スキル。
`references/japanese-writing-practices.md` を規約の源泉とし、日本語として適切で読みやすい文書を保証する。

## 必須リファレンス

**作業開始前に必ず `references/japanese-writing-practices.md` を読み込むこと。**
文体・文構造・冗長表現・漢字の開き・表記ゆらぎ・重大度の基準すべてがこの文書に定義されている。

| ファイル | 内容 |
|---|---|
| `references/japanese-writing-practices.md` | 全モードで必読の日本語ライティング規範 |

## モード判定

冒頭でユーザーの依頼からモードを判定する。あいまいな場合のみ推奨案を含む選択肢を提示して確認する。

| キーワード例 | モード |
|---|---|
| 書いて / 作成して / まとめて / ドキュメント化して | Mode 1: 新規作成 |
| 添削して / 直して / 校正して / 推敲して / 改善して | Mode 2: 添削 |
| 検証して / チェックして / 確認して / レビューして / `--verify` | Mode 3: 検証 |

Mode 2 と Mode 3 の違いは「ファイルを修正するか」。修正を求められていない依頼は Mode 3 とする。

## textlint によるチェックの補完（ハイブリッド方式）

Mode 2・Mode 3 では、LLMレビューの前に textlint の利用可否を確認し、使えれば機械的チェックとして併用する:

1. **利用可否の確認**: プロジェクトに `.textlintrc*` があり、`npx --no-install textlint --version` が成功するか確認する
2. **利用可能な場合**: `npx --no-install textlint <対象ファイル>` を実行し、結果を指摘に取り込む（ルールID付きで出典を明示）
3. **利用不可の場合**: インストールはせず、リファレンス規範に基づくLLMレビューのみで検証する。レポートに「textlint未使用」と明記する

textlint はあくまで補完。textlint が通っても、係り受け・曖昧さ・構成などLLMでしか判断できない観点は必ず検証する。

## Mode 1: 新規作成

日本語規範に沿った文書を新規に書く。

### 手順

1. **要件の把握**: `$ARGUMENTS` またはユーザーの依頼から、文書の目的・読者・種別（README/設計書/手順書等）・出力先パスを整理する。不明な点は確認する
2. **リファレンス読込**: `references/japanese-writing-practices.md` を読み込む
3. **文体の決定**: ユーザー指定 > 同一プロジェクトの既存文書の文体 > リファレンスの文書種別既定、の優先順で決める
4. **構成設計**: 見出し構成を先に決める（結論先行、前提条件は冒頭）
5. **執筆**: 規範に準拠して書く
6. **セルフ検証**: 書き上げた文書に対して Mode 3 の検証観点を自己適用し、指摘が出なくなるまで修正してから納品する

### 執筆時の必須チェックリスト

- 一文100文字以下、読点は一文に3つまで
- 文体（です・ます / である）を地の文で統一
- 「〜することができる」「〜を行う」等の冗長表現を使わない
- 副詞・形式名詞・補助動詞はひらがなに開く（こと、とき、ください、また 等）
- 固有名詞は公式表記（GitHub、JavaScript、Node.js 等）
- カタカナ長音・和欧文間スペースを文書内で統一

## Mode 2: 添削

既存の日本語文書をレビューし、修正する。

### 手順

1. **対象の特定**: `$ARGUMENTS` のパスまたはユーザー指示から対象を決定し、全文を読み込む
2. **リファレンス読込**: `references/japanese-writing-practices.md` を読み込む
3. **文体判定**: 対象文書の基準文体をリファレンスの手順で判定する
4. **textlint実行**: 上記ハイブリッド方式に従う
5. **指摘の収集**: 検証観点（Mode 3 参照）で全指摘を重大度付きで洗い出す
6. **修正方針の確認**: 指摘件数が多い場合（目安: [重大]+[推奨]が10件超）や、意味が変わる可能性のある修正が含まれる場合は、修正方針の要約を提示して承認を得てから修正する。軽微な修正のみなら直接修正してよい
7. **修正の実施**: Edit で修正する。**意味・技術的内容は変更しない**。表現の変更で意味が変わる恐れがある箇所は修正せず指摘に留める
8. **修正レポート**: 修正内容を重大度別にまとめて報告する

### 添削の原則

- 誤りの修正と読みやすさの改善に徹し、書き手の文章の個性・構成意図は尊重する
- Markdownのコードブロック・コマンド例・引用文の中は修正しない（誤字が明白な場合のみ指摘）
- 対象文書がすでに一貫したスタイル（例: 長音省略で統一）を持つ場合は、規範よりも文書内の統一を優先する

## Mode 3: 検証

文書を検証し、レポートのみ出力する。**ファイルは修正しない。**

### 手順

1. **対象の特定と読込**: 対象ファイルの全文を読み込む
2. **リファレンス読込**: `references/japanese-writing-practices.md` を読み込む
3. **文体判定**: 基準文体を判定する
4. **textlint実行**: 上記ハイブリッド方式に従う
5. **検証**: 以下の観点で全文を検証する
6. **レポート出力**: 下記形式で報告する

### 検証観点

| カテゴリ | チェック項目 |
|---|---|
| **正確さ** | 誤字脱字 / 同音異義語 / 二重否定 / ら抜き言葉 / 主語の欠落・曖昧さ |
| **文構造** | 一文100文字以下 / 読点3つまで / 係り受けの明確さ / 助詞・接続詞の連続 |
| **文体** | です・ます / である の統一 / 箇条書き内の文法構造の統一 |
| **簡潔さ** | 冗長表現 / 「こと」「もの」の多用 / 不要な「〜という」 |
| **表記** | 漢字の開き / 表記ゆらぎ / カタカナ長音 / 全角半角 / 固有名詞の公式表記 |
| **構成** | 1段落1トピック / 見出しレベル / 結論先行 / 前提条件の位置 |

### レポート形式

```markdown
## 検証結果: <ファイル名>

### 総評
（基準文体の判定結果と、全体の品質・最も重要な改善点を1〜2文で）

### 指摘事項
- **[重大]** L<行>: 〜（指摘内容と修正案）
- **[推奨]** L<行>: 〜
- **[軽微]** 〜（同種の指摘は「表記ゆらぎ: サーバ/サーバー 混在（L10, L25, L48）」のようにまとめる）

### textlint結果
（実行した場合のみ。未使用の場合は「textlint未使用（LLMレビューのみ）」と記載）

### 良い点
（規範に準拠している点、読みやすく工夫されている点）
```

指摘ゼロの場合もその旨を明記し、良い点を報告する。

## 共通の品質基準

- 指摘には必ず**具体的な修正案**を添える（「読みにくい」だけの指摘はしない）
- 同種の軽微な指摘は行番号をまとめて1件として報告し、レポートの見通しを保つ
- 重大度の判定はリファレンスの定義に厳密に従う
- 技術用語・コード識別子・固有名詞は翻訳や言い換えをしない
- 判断が規範にない場合は、JTF日本語標準スタイルガイドの一般原則（読者にとっての読みやすさ最優先）に従い、根拠を明示する
