# PR Fixer

指定された外部指摘を事実として扱わず、PRの目的、既存の公開契約、PR差分、現在のコード、テストと失敗ログで独立に検証する。根拠が確認できた問題だけを最小限に直す。

## 呼び出し

```text
$pr-fixer <PRレビューコメントURL or PRのCI失敗URL> [--commit | --commit-push | --commit-push-reply] [--auto] [--request-review] [--no-agent] [--issue <Issue URL | ファイルパス>] [--guidelines <パス[,パス...]>]
```

位置引数は1つだけ必須とする。

- `<PRレビューコメントURL>`: PR上の `discussion_r...`、`issuecomment-...`、`pullrequestreview-...` のいずれかを含むURL
- `<PRのCI失敗URL>`: GitHub Actionsのrun/job URL、または失敗checkを一意に特定できるPR checks URL

PRトップURLだけでコメントまたは失敗checkを一意に特定できない場合は、候補を提示して選択を求める。URLと現在のリポジトリが異なる場合は、対象を推測しない。

### オプション

- `--auto`: 修正計画と検証結果を提示し、定例の承認待ちを省略する。commit・push・PR本文更新・返信・review requestの範囲は、指定された後処理オプションで決まる。
- `--commit`: Phase 8で今回の変更だけをステージし、セッション固有の一時ファイルへConventional Commits形式のコミットログを出力して `git commit -F` を実行する。
- `--commit-push`: `--commit` を暗黙に有効化し、コミット成功後に対象PRのheadブランチへ通常の `git push` を実行する。push成功後、修正後のPR全体の差分と検証結果に合わせてPR本文を更新し、`--issue` 指定時はIssue本文を同期する。force pushは行わない。
- `--commit-push-reply`: レビューコメントURL専用。コード変更がある場合は `--commit-push` の全手順の完了後に、修正内容と検証結果を返信する。修正不要など、コードを変更しない判断が確定した場合は、commit・push・PR本文更新・Issue本文の同期を行わず、修正しなかったことと判断理由を返信する。`discussion_r<ID>` のURLは、対象が返信ならその `in_reply_to`、それ以外なら `ID` をスレッド先頭コメントIDとして同じレビューthreadへ返信する。`issuecomment-<ID>` と `pullrequestreview-<ID>` のURLは、次の形式でPRへ新規コメントを投稿する。

  ```text
  > {レビューコメントURL}

  {返信コメント}
  ```

- `--request-review`: `--commit-push-reply` との併用時だけ有効。返信投稿成功後、元コメントのユーザーがbotではなく、当該PRの既存reviewのauthor集合に含まれる場合だけreview requestする。
- `--no-agent`: `task-artifact-fixer` との呼び出し互換性のため受理するが、処理は変えない。
- `--issue <Issue URL | ファイルパス>`: 対応するIssueを判断材料として読み込む。コード変更がある場合は、fix後もIssue本文がWhat/Whyの正本（single source of truth）になっているかを確認し、`--commit-push` または `--commit-push-reply` 指定時は本文を同期する。それ以外の場合は更新案の提示に留める。修正対象は変えない。

`--commit-push-reply` と他のcommit系オプションが併記された場合は `--commit-push-reply` として扱う。`--commit-push-reply` をCI失敗URLと併用した場合、および `--request-review` を `--commit-push-reply` なしで指定した場合は、外部操作を行わず入力エラーとして扱う。commit系オプション未指定の場合は、Phase 8で対象ファイルのステージングとコミットログファイルの出力まで行う。

`--auto` の有無にかかわらず、対象や重要な仕様が確定できない場合、権限が不足する場合、既存のユーザー変更と重なる場合、依頼範囲の拡張や未承認の破壊的操作が必要な場合は、その判断に必要な情報を示して確認する。

### 追加の作業ガイドライン

`--guidelines` はカンマ区切りのローカルファイルパスを受け取る。各パスの前後の空白を除き、相対パスは呼び出し時のカレントディレクトリを基準に解決する。
指定時は作業の冒頭ですべての指定ファイルを読み、指定された指摘・CI失敗の調査、修正・検証と指定された後処理に適用する。操作の許可はユーザーの依頼と既存オプションに従う。
空のパス、読込失敗、解消できない指示の競合があれば、該当箇所と理由を示し、影響する作業を進める前にユーザーに確認する。

### Issueコンテキスト

`--issue` は対応するIssueのURLまたはローカルファイルパスを受け取る。相対パスはスキル呼び出し時のカレントディレクトリを基準に解決する。
指定時は妥当性・根本原因の判定や修正の前に、URLなら利用可能な連携ツールまたはCLIでIssueのタイトル・本文を取得し、ファイルなら内容を読む。理解に必要なコメント・参照資料も読み、目的・背景・要件・受け入れ条件を整理する。
読み取ったコンテキストを期待動作の判断と最小修正に使い、指定コメント・CI失敗と無関係なIssue要件の実装へ広げない。
指定内容を取得・読込できない場合は原因と不足情報を示して確認し、Issueを理解した前提で作業を進めない。
コード変更がある場合は、fix内容とIssue本文の整合をPhase 7で判定し、Phase 8の「Issue本文の同期」に従って反映する。

## スコープ

### 含むもの

- PRの目的・既存契約・現在コードを基準にした、指定レビューコメントの妥当性検証
- PR差分・失敗ログ・対象コードを根拠にした、指定CI失敗の原因特定
- 妥当と判定した問題への最小修正、回帰テスト、Lint・型チェック
- オプションに応じたcommit・pushとpush後のPR本文更新、指定コメントへの返信、条件付きreview request
- `--issue` 指定時の、fix内容に合わせたIssue本文の同期と、必要な場合だけのdecision historyコメント投稿

### 含まないもの

- `--issue` で指定されたIssueと理解に必要な参照資料を除く、タスク文書・進捗正本・受け入れ条件の読込と、これらの文書の更新
- 「Issue本文の同期」の範囲を超えるIssueの操作（今回のfixと無関係な記述の整理、状態変更・close、label等のメタデータ変更）
- PR全体の新規レビューや、指定URL以外のレビュー指摘・CI失敗の便乗修正
- conversationのresolve、workflowの再実行、approve、merge、close、rebase、force push
- 指定問題と無関係なリファクタリングやフォールバック追加

## 実行原則

1. **外部指摘を事実として扱わない。** コメントや失敗ログを調査開始点とし、PRの目的・既存契約・PR差分・現在コード・再現結果で独立検証する。
2. **根本原因へ直接対応する。** 症状を隠すskip、retry、条件緩和、エラー握り潰しを、要件なしに追加しない。
3. **変更を指定対象へ限定する。** 別の問題は「気づきメモ」として報告し、その場で修正しない。
4. **ユーザー変更を保持する。** dirty working treeを確認し、重なる未コミット変更がある場合は編集前に相談する。stash・reset・checkoutを無断実行しない。
5. **公開情報と作業証跡を分離する。** PR本文・返信にはローカルパス、内部の作業管理情報、未確認の事実を含めない。

## ワークフロー

### Phase 1: 入力と作業状態を確定する

1. URLと各オプションを解析する。不足・不明・競合があれば推測せず確認する。`--commit-push-reply` ではレビューコメントURLであること、`--request-review` が指定される場合は `--commit-push-reply` も指定されることを確認する。
2. `git rev-parse --show-toplevel`、`git status --short --branch`、`gh auth status` を確認する。
3. URLから `owner/repo`、PR番号、対象ID（comment / review / run / job / check）を抽出する。
4. `gh pr view` でPRのstate、title、body、head/baseブランチ、head SHA、head repositoryを取得し、ローカルのbranch・HEAD・remoteと照合する。`--request-review` 指定時は既存reviewのauthor集合も取得し、元コメント投稿者がこの集合に含まれるかだけを判定する。
5. ローカルがPR headと一致しない場合は編集せず、安全な切替・更新方法を提示して確認する。
6. PRが `CLOSED` または `MERGED` の場合は既定で読み取り専用の検証に留める。別ブランチでの追補修正を求められた場合だけ、対象ブランチとスコープを確認して続行する。

### Phase 2: PRとプロジェクトの判断材料を取得する

1. リポジトリ直下から対象へ適用される `AGENTS.md`、開発・テスト規約を読む。
2. `--issue` 指定時は「Issueコンテキスト」に従って読み込む。PRのtitle・bodyと差分、読み取ったIssueから変更目的と期待動作を整理する。目的の説明だけで正しさを判断しない。
3. 指摘箇所の現在コードと呼び出し元、関連テスト、公開仕様・設定・既存の契約を読む。期待動作を裏付ける資料が不足する場合は、仕様判断が必要な状態として扱う。

### Phase 3: 対象の一次証拠を収集する

#### レビューコメントモード

1. URLアンカーに応じてコメント本文とメタデータを取得する。
   - `discussion_r<ID>`: `gh api repos/{owner}/{repo}/pulls/comments/{ID}`
   - `issuecomment-<ID>`: `gh api repos/{owner}/{repo}/issues/comments/{ID}`
   - `pullrequestreview-<ID>`: `gh api repos/{owner}/{repo}/pulls/{PR}/reviews/{ID}`
2. コメントのauthor login/type、作成時刻、対象path/line、commit ID、in_reply_to、outdated/resolved相当の状態を保持する。bot判定にはAPIの `user.type == "Bot"` とlogin末尾の `[bot]` の両方を使う。
3. 同じthreadの前後コメント、PR差分、コメント対象ファイルのPR head版とローカル版を読む。
4. サマリコメントの場合は、本文中の各主張を列挙するが、指定コメント外のthreadへ対象を広げない。

#### CI失敗モード

1. PR checks URLなら `gh pr checks` から失敗checkと実行URLを解決する。run URLならjob一覧、job URLなら対象jobを取得する。
2. 失敗jobが複数ある場合は独立原因か連鎖失敗かを切り分け、先行する根本原因を優先する。
3. GitHub Actionsログを次の順で調べる。
   - エラー語、失敗テスト名、例外名の前後を抽出する。
   - ログ末尾で終了コード、失敗件数、timeout、OOM、cancelを確認する。
   - 情報が一致しない、または原因チェーンが不足する場合だけ完全な失敗ログを段階的に読む。
4. matrix jobでは全環境共通か、OS・ランタイム版固有かを比較する。
5. GitHub Actions以外のcheckでログを取得できない場合は、提供元URLと不足情報を報告し、ログ提供を依頼する。推測で編集しない。

巨大ログを一度に会話へ展開しない。一時保存が必要ならセッション固有の一時ディレクトリを使い、必要行だけ読む。

### Phase 4: 妥当性と根本原因を判定する

#### レビューコメントの分類

コメントの各主張を、次のいずれかへ分類する。

- **妥当**: PRの目的または既存契約に反し、現在のPR headでも問題が再現する。
- **部分的に妥当**: 問題はあるが、提案された範囲・修正方法の一部が過剰または目的外である。
- **対応済み・outdated**: 後続commitで問題が解消されている。
- **不当**: コメントの前提がコード・仕様・テスト事実と一致しない。
- **仕様判断が必要**: 複数の解釈が成立し、既存契約・PRの目的・テストでは決められない。

判定前に、コメントが要求する期待動作を一文で言い換え、対象コードと呼び出し元、関連テスト、PRの目的、既存契約を突き合わせる。提案コードはそのまま採用せず、反証となるケースも確認する。

#### CI失敗の分類

失敗を次のいずれかへ分類する。

- **PR変更による回帰**
- **リポジトリ内のworkflow・依存・設定不備**
- **flaky・並列干渉**
- **runner・権限・secret・外部サービス等の環境要因**
- **PRと無関係な既存障害**
- **原因未確定**

ログ、PR差分、対象コード、同一checkの他matrix結果で因果関係を説明する。再実行だけで消えそうという理由でflakyと断定しない。指定問題の根本原因を直接解消するリポジトリ内修正だけを編集対象とする。

#### 判定後の分岐

- `妥当`、`部分的に妥当`、`PR変更による回帰`、`リポジトリ内の不備`: 根拠と最小修正計画を提示する。`--auto` 指定時はそのままPhase 5へ進み、未指定時はユーザー承認を得てから進む。
- `対応済み・outdated`、`不当`、環境要因、無関係な既存障害: コードを変更せず、Phase 7で根拠と推奨アクションを報告する。
- `仕様判断が必要`、`原因未確定`: 不足情報と推奨案を示して確認する。推測で修正しない。

修正計画には、変更対象、変更理由、追加・更新するテスト、実行する検証、スコープ外の発見を含める。

### Phase 5: 最小修正を実装する

1. 編集対象ファイルを編集直前に読み直す。
2. 原因へ直接対応する最小差分を実装する。本番コードを変更する場合は、問題を再現して修正後に通る回帰テストを可能な範囲で追加する。
3. 自動生成物は所定の生成コマンドで更新し、直接編集しない。
4. 指定対象と無関係な発見は変更せず、結果報告の気づきメモへ残す。

### Phase 6: 修正を検証する

1. 指摘またはCI失敗を再現する最小のテストを最初に実行する。
2. 変更対象に近い軽量テスト、リポジトリ所定のLint・型チェック・format check、`git diff --check` を実行する。
3. CI固有条件をローカルで完全再現できない場合は、ローカルで確認できた範囲と未検証条件を分離する。
4. DB、コンテナ、外部API等を使う重いテストは既定でskipする。実行が必要な場合、`--auto` 指定時は共有環境や外部サービスへの影響がないローカル検証、または実行許可を得ている検証を実行する。それ以外は事前に承認を得る。
5. 失敗した検証はエラーメッセージを正確に読み、原因特定後に修正して再実行する。3回修正しても解決しない場合は続行判断を求める。
6. `git diff` と `git status --short` で依頼外変更の混入とユーザー変更との重複がないことを確認する。

### Phase 7: 作業結果をレビューする

次の形式で結論から報告する。コード変更がある場合、`--auto` 指定時は中間報告として提示し、承認を待たずPhase 8へ進む。未指定時は最終承認を得てから進む。この承認はIssue本文の更新案とdecision historyコメント案にも適用する。

コード変更があり `--issue` が指定されている場合は、Phase 8の「Issue本文の同期」の判定基準で更新要否とコメント要否を決め、更新が必要な場合は更新後の本文全体をセッション固有の一時ファイルへ保存して報告に含める。`--commit-push` と `--commit-push-reply` のどちらも指定されていない場合は、この更新案を最終結果とする。

```markdown
## 判定
- 対象: {コメント / check名}
- 分類: {分類}
- 根拠: {PRの目的・コード・既存契約・ログ・テストの対応}

## 修正内容
- `{path}`: {最小修正の概要}

## 検証結果
- 対象テスト: `{command}` → {PASS/FAIL}
- Lint・型・format: `{command}` → {PASS/FAIL/SKIP}
- 重いテスト・CI固有条件: {SKIPまたは結果と理由}

## 気づきメモ
- {スコープ外の発見、または「なし」}

## Issue本文（`--issue` 指定時）
- 判定: {更新が必要 / 変更不要}: {What/Whyへの影響と理由}
- 更新案: {変更する節と変更前後の要旨、本文全体のファイル}
- decision historyコメント: {投稿案 / 不要と判断した理由}

## 外部操作
- PR本文更新・Issue本文更新・Issueコメント投稿・PRコメント返信・review request・resolve・workflow再実行: 未実施
```

修正不要など、コードを変更しない判断が確定した場合は、コード差分を前提とする後処理を省略する。`--commit-push-reply` 指定時は、Phase 1で読み取り専用とした場合を除き、調査結果の報告後にPhase 8の「PRコメントへの返信とreview request」へ進む。それ以外は調査結果を報告して終了する。

### PRコメント返信の記述

PRコメント返信は、ローカル環境を知らないレビュアーが単独で読んでも理解できる公開文書として作成する。

- 結論、対応内容、検証結果をこの順で簡潔に書く。コードを変更しない場合は、修正しなかったことを明記し、その判断理由を確認できた事実に基づいて伝える。
- ローカルパス、内部の作業項目・受け入れ条件・進捗・ログ、未確認の事実を本文へ書かない。
- 読み手が確認できるPR差分内のファイルパスやコード識別子は、必要な場合だけ使う。専門用語や略語は初出時に短く説明し、主語・条件・結果を省略しない。

投稿直前に、記載した事実をPR差分・コード・検証結果で裏付けられることを確認する。満たさない場合は、投稿前に書き直す。

### Phase 8: 指定された後処理を行う

#### ステージング・commit・pushと本文更新

コード変更があり、Phase 7の進行条件を満たした場合に次を実行する。

1. `.git/hooks/pre-commit` と `.githooks/pre-commit` を確認する。存在する場合は内容を読み、定義されたformat・Lint等を `git add` 前に直接実行して成功させる。
2. 今回変更したコード・テスト・設定だけを `git add` する。ユーザーの未コミット変更や作業証跡はステージしない。
3. セッション固有の一時ファイルへ、Conventional Commits形式・各行72文字以内のコミットログを出力する。メッセージへローカル一時ファイルのパスを含めない。
4. オプションに従う。
   - commit系オプション未指定: ステージングとログ出力で終了する。
   - `--commit`: `git commit -F {log_path}` を実行し、commit SHAを報告する。
   - `--commit-push` / `--commit-push-reply`: commit成功後、URLから確認したPR head repository・branchとpush先が一致することを再確認し、通常の `git push` を実行する。upstream未設定時だけ `git push -u {remote} {branch}` を使う。push成功後、下記「PR本文の更新」を実行し、`--issue` 指定時は続けて「Issue本文の同期」を実行する。
5. commit、push、PR本文・差分の取得、PR本文の更新・反映確認、またはIssue本文の同期が失敗した場合は、その時点で返信を含む後続の外部操作を行わず、正確なエラーと残作業を報告する。force push、別remoteへのpush、認証変更で回避しない。

#### PR本文の更新

1. push成功後、`gh pr view {PR} --repo {owner}/{repo} --json body,baseRefOid,headRefOid` で最新のPR本文とbase/headのSHAを取得し、それぞれ `{base_sha}`・`{head_sha}` として保持する。head SHAが今回pushしたcommit SHAとローカルHEADの両方に一致することを再確認する。不一致なら本文更新と後続の外部操作を停止し、差異を報告する。
2. base/headのcommitとmerge-baseをローカルで参照できることを確認する。不足するcommit・履歴は、確認済みのbase/head repositoryから必要なrefをfetchする。shallow cloneではmerge-baseを求めるために必要な履歴を追加取得する。揃わなければ差分取得失敗として扱う。
3. GitHubの差分取得上限を避けるため、`git diff --stat {base_sha}...{head_sha}` の3点比較でPR全体の変更概要を把握する。差分全体を一度に会話へ展開せず、本文更新に必要なファイル・箇所を `git diff {base_sha}...{head_sha} -- {paths}` などで段階的に読む。
4. 最終差分と確認済みの検証結果を根拠に、今回の修正によって古くなった概要・変更点・検証結果を更新する。既存の構成、背景説明、関連リンクなど修正と無関係な情報は保持する。上記「PRコメント返信の記述」の公開情報に関する制約をPR本文にも適用する。
5. 既に内容が整合していれば変更不要と判断し、その理由を記録する。変更が必要なら更新後の本文全体をセッション固有の一時ファイルへ保存し、`gh pr edit {PR} --repo {owner}/{repo} --body-file {body_path}` で反映する。
6. 更新後にPR本文を再取得し、意図した内容が反映されていることを確認する。取得失敗や不一致は未完了として扱い、後続のIssue本文の同期・返信・review requestへ進まない。

#### Issue本文の同期

`--issue` 指定時に、PR本文の更新・反映確認の後で実行する。目的は、fix後もIssue本文だけを読めばWhat（要件・スコープ・受け入れ条件）とWhy（目的・背景）が正しく分かる状態を保つことである。How（実装方法・修正内容）はPR本文とコードに任せ、Issue本文へ足さない。

1. Phase 7の更新要否の判定を前提にする。更新が必要なのは、今回のfixで次のどちらかが起きた場合だけとする。
   - 要件・スコープ・受け入れ条件が変わった、または曖昧だった点が確定した。
   - 目的・背景の記述がfix後の結論と矛盾する、または判断の前提が変わった。

   実装だけを直してWhat/Whyが変わらない場合は「変更不要」とし、理由を記録する。今回のfixと無関係な記述の整理や、既存のHow記述の削除は行わず、必要なら気づきメモへ残す。
2. 更新直前に最新の本文を取得する。GitHub Issueは `gh issue view {issue_number} --repo {issue_owner}/{issue_repo} --json body`、GitHub以外のURLは利用可能な連携ツール、ファイルは再読込を使う。Phase 7の更新案は最新本文を基に作り直し、提示内容から変わる場合は、`--auto` 未指定なら反映前に再承認を得る。
3. 既存の構成・記法・言語を保ち、該当箇所だけを書き換える。本文には現在の正しい状態だけを書き、「〜から変更した」のような変更履歴は書かない。変更の経緯はdecision historyコメントへ分ける。「PRコメント返信の記述」の公開情報に関する制約をIssue本文とコメントにも適用する。
4. 反映する。GitHub Issueは更新後の本文全体をセッション固有の一時ファイルへ保存し、`gh issue edit {issue_number} --repo {issue_owner}/{issue_repo} --body-file {body_path}` を実行する。ファイル指定時はそのファイルを直接編集し、commitにはステージしない。連携ツールで更新できない場合は未完了として扱い、更新案を報告する。
5. 反映後に本文を再取得または再読込し、意図した内容になっていることを確認する。取得失敗や不一致は未完了として扱い、コメント投稿と後続の外部操作へ進まない。
6. decision historyコメントは、本文の差分だけでは「なぜ変えたか」を後から追えない場合だけ投稿する。例として、要件を縮小・変更した場合、複数案から1つを選んだ場合、レビュー指摘を受けて受け入れ条件を変えた場合が該当する。誤字修正や、PRを読めば理由が自明な明確化では投稿しない。
   - コメントには、変更した点、理由、根拠（PR・レビューコメント・CIのURL）を簡潔に書く。
   - GitHub Issueは本文をセッション固有の一時ファイルへ保存し、`gh issue comment {issue_number} --repo {issue_owner}/{issue_repo} --body-file {comment_path}` で投稿する。GitHub以外のURLは利用可能な連携ツールで投稿する。
   - ファイル指定時はコメントを投稿せず、変更理由を結果報告へ書く。

#### PRコメントへの返信とreview request

`--commit-push-reply` 指定時に実行する。コード変更がある場合は、PR本文の更新・反映確認と `--issue` 指定時のIssue本文の同期（いずれも変更不要の確認を含む）まで完了してから進む。コードを変更しない判断が確定し、Phase 7から直接進んだ場合は、commit・push・本文更新を行わずに返信する。

1. Phase 7で報告した判定・修正・検証結果に基づき、「PRコメント返信の記述」に従って返信本文を作成する。
2. `discussion_r<ID>` なら、対象コメントが返信の場合は `in_reply_to`、それ以外は `ID` をスレッド先頭コメントIDとして `gh api repos/{owner}/{repo}/pulls/{PR}/comments -f body={reply} -F in_reply_to={thread_root_id}` で同じthreadへ投稿する。それ以外なら `gh pr comment {PR} --body {quoted_reply}` で引用付き新規コメントを投稿する。投稿に失敗した場合はreview requestを行わず、投稿先・エラー・残作業を報告する。
3. `--request-review` 指定時は、返信投稿の成功後に限り、元コメント投稿者がbotでなく、Phase 1で取得した既存reviewのauthor集合に含まれる場合は `gh pr edit {PR} --add-reviewer {login}` でreview requestする。ユーザーが集合に含まれない場合とbotの場合はrequestを行わず、その理由を報告する。review requestだけが失敗した場合は、返信済みであることとエラーを分けて報告する。

#### 後処理の結果報告

commit・push・PR本文更新・Issue本文の同期・返信・review requestの結果を区別して報告する。commitした場合はSHAを、修正不要などでcommit・pushを省略した場合はその理由を示す。PR本文とIssue本文は「更新済み」「変更不要」「未完了」「対象外」、decision historyコメントは「投稿済み」「不要」「未完了」「対象外」のいずれかと根拠を示す。

## エラーハンドリング

| 状況 | 対応 |
|---|---|
| URLから対象を特定不能 | PR内の候補URL・check名を提示して選択を求める |
| コメントが削除済み・権限不足 | APIエラーを提示し、本文またはアクセス権の確認を依頼する |
| PRがclosed・merged | 読み取り専用で判定し、追補修正が必要なら別ブランチで続けるか確認する |
| ローカルHEADとPR head不一致 | 編集を停止し、安全なbranch切替・更新方法を確認する |
| dirty working tree | 重複の有無を調べ、重なる場合だけstash・commit・中断の判断を求める |
| CIログ取得不能 | check提供元とURLを提示し、ログ提供を依頼する |
| `--commit-push-reply` とCI失敗URLの併用 | 入力エラーとして、レビューコメントURLを指定するよう案内する |
| `--request-review` の単独指定 | 入力エラーとして、`--commit-push-reply` との併用を案内する |
| PR本文・差分の取得、本文の更新・反映確認失敗 | Issue本文の同期・返信・review requestを行わず、push済みであること、エラー・不一致、本文更新の残作業を分けて報告する |
| Issue本文の取得・更新・反映確認、Issueコメント投稿の失敗 | 返信・review requestを行わず、push・PR本文更新の結果、エラー・不一致、Issueの残作業と更新案を分けて報告する |
| 返信投稿失敗 | review requestを行わず、投稿先・エラー・commit/pushの成否を分けて報告する |
| review request失敗 | 返信済みの状態を保持し、エラーと手動で依頼する対象ユーザーを報告する |
| diffが想定より大きい | 原因仮説と依頼範囲を見直す。範囲の拡張が必要な場合と、`--auto` 未指定で500行を超える場合は、続行前に承認を得る |
| ローカル検証失敗 | commit・pushせず、原因調査へ戻る |

## 禁止事項

- 検証前にレビュー提案コードを適用しない。
- CIを通すためだけにテスト削除、skip追加、閾値緩和を行わない。
- 機密情報をログへ保存またはコードへハードコードしない。
- commit系オプション未指定でcommit、`--commit-push` または `--commit-push-reply` なしでpush・PR本文更新・Issue本文更新・Issueコメント投稿を行わない。
- PRコメント返信は、`--commit-push-reply` を指定した場合にPhase 8の手順に沿って実行する。
- review requestは、`--request-review` と `--commit-push-reply` を指定し、Phase 8の返信投稿とreview requestの条件を満たした場合に実行する。
- ユーザー承認なしにconversationのresolve・workflow再実行を行わない。
- `git reset --hard`、無断stash、無断checkout、force pushを行わない。
