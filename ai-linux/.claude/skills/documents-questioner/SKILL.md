# Documents Questioner

複数ソースを読み込んだAIへ渡す、コピー可能な質問プロンプトを生成する。ソースの分析結果そのものを回答せず、ユーザーが欲しい情報を根拠付きで引き出す質問を設計する。

## 基本方針

- ユーザーの目的、利用場面、判断したいことを質問の中心に置く。
- ソースの記述、AIによる分析、AIによる提案を分離させる。
- 重要な主張へ根拠ソースを対応付け、記載がなければ「記載なし」、判断不能なら「情報不足」と回答させる。
- 合意だけでなく、対立、前提条件、適用範囲、例外、不確実性も確認させる。
- ソースの内容や利用できる引用位置を見ていない場合、それらを推測してプロンプトへ書かない。

詳細な原則は必ず [01-principals.md](references/01-principals.md) を読む。質問の3層設計には [02-basic-design.md](references/02-basic-design.md)、共通指示の組み立てには [03-master-prompt.md](references/03-master-prompt.md) を読む。

## 生成フロー

### 1. 依頼を構造化する

会話から次を抽出する。明示されていない項目は、結論へ影響するものだけ確認する。確認できない場合は安全な仮定を明記するか、`[入力してください]` のプレースホルダーを残す。

- 目的: 何を知り、判断し、実行したいか
- Context: 対象、現状、課題、制約、既決事項、対象外
- ソース: 種類、範囲、名称、時点、対象バージョン
- 分析: 要約、比較、根拠評価、批判、意思決定、実践、追加調査のどれか
- 成果物: 表、要約、チェックリスト、Decision Matrix、ロードマップなど

質問が必要なら一度に3問以内へまとめる。ユーザーが「すぐ作って」と求める場合は確認で止めず、プレースホルダー付きで生成する。

### 2. 実行方式を選ぶ

依頼の複雑さに応じて、次の最小構成を選ぶ。

- **単発プロンプト**: 目的と出力が明確で、1回の回答で扱える場合
- **段階プロンプト**: 多数・異種のソース、重要な意思決定、対立や信頼性評価、実行計画まで扱う場合
- **質問発見プロンプト**: 調査目的はあるが、何を尋ねるべきか未確定の場合
- **検索計画プロンプト**: 読み込ませるソース自体を追加収集したい場合

段階構成を選ぶときは [07-recommendation-flow.md](references/07-recommendation-flow.md)、質問発見には [09-meta-template.md](references/09-meta-template.md)、検索計画には [08-search-template.md](references/08-search-template.md) を読む。短時間で汎用質問を作る場合は [12-minimum-general-template.md](references/12-minimum-general-template.md) を基礎にする。

### 3. 分析・観点・出力を選ぶ

`Universal Analysis × Domain Lens × Output` の順で必要な要素だけ選ぶ。テンプレートを機械的に連結せず、重複する指示を統合する。

- 分析課題の選定には [04-universal-analysis.md](references/04-universal-analysis.md) を読む。
- ソフトウェア、事業、組織、学術研究などの観点追加には [05-domain-lens.md](references/05-domain-lens.md) を読む。
- 実務成果物の形式指定には [06-output.md](references/06-output.md) を読む。

ユーザーが指定していない観点を盛り込みすぎない。目的に直接必要な分析課題を優先し、通常は3〜6個に絞る。

### 4. コピー可能なプロンプトへ組み立てる

プロンプトへ必要な範囲で次を含める。

1. **Role**: 読み込まれたソースを根拠に整理・比較する役割
2. **Goal**: 回答によって達成したい判断または成果
3. **Context**: 結論を左右する背景と制約
4. **Source scope**: 対象ソースと、外部知識を使ってよい範囲
5. **Tasks**: 実行順が分かる具体的な分析指示
6. **Grounding rules**: 根拠、区分、情報不足、対立、適用条件の扱い
7. **Expected output**: 見出し、表の列、粒度、優先順
8. **Next step**: 必要に応じた追加質問、検証、見直し条件

対象AIにソース限定回答を求める場合は、外部知識を混ぜず、使用した場合だけ明示させる。外部知識も必要な場合は「ソース由来」と「外部知識」を別枠にさせる。

### 5. 媒体に合う根拠位置を指定する

対象AIが利用できる識別情報に合わせ、重要な主張へ次の位置情報を付けさせる。利用できない位置情報を捏造させない。

| 媒体 | 根拠位置の例 |
|---|---|
| PDF・文書 | 文書名、章・節、ページ |
| Web | ページタイトル、URL、公開日・更新日、節 |
| 動画・音声 | タイトル、話者、タイムスタンプ |
| テキスト・議事録 | ファイル名、見出し、発言者、該当箇所 |

引用は表現自体が重要な箇所に限定し、通常は主張と根拠の対応付けを優先する。対象AIが位置情報を提示できない場合は、利用可能なソース名だけを要求する。

### 6. 出力する

原則として次の順で提示する。

1. `## 生成したプロンプト`
2. コピー用の `text` コードブロック
3. 段階方式なら、実行順に分けた複数のコードブロック
4. 未確定事項がある場合だけ `## 入力・確認が必要な項目`

プロンプト設計の長い解説は付けない。ユーザーが複数案を求めた場合だけ、簡潔版と高精度版など用途の異なる案を示す。

## 品質確認

出力前に [11-failure-example.md](references/11-failure-example.md) を参照し、次を満たさなければ修正する。

- 目的と期待する成果物が明確か。
- 主張へ根拠を対応付ける指示があるか。
- Source / Analysis / Recommendationを区別できるか。
- 「記載なし」「情報不足」を許容しているか。
- 対立、適用条件、例外、結論を変えうる情報を扱えるか。
- 媒体に適した根拠位置を求め、存在しない位置情報を要求していないか。
- 質問数と出力粒度が目的に対して過剰でないか。

重要な意思決定、高い正確性が必要な調査、またはユーザーが監査を求める場合は、[10-self-review-template.md](references/10-self-review-template.md) を基に回答監査用の追質問も生成する。

## 禁止事項

- 読み込んでいないソースの内容、引用、ページ、タイムスタンプを作らない。
- ユーザーが求めていない最終結論やソース分析を代行しない。
- すべてのテンプレートを毎回含めない。
- 根拠のない精密なスコア、閾値、因果関係を事実として求めない。
- 対象AIがアクセスできると確認していないURLや添付を、閲覧済みと仮定しない。
