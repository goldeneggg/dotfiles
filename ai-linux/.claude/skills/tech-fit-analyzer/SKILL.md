# Tech Fit Analyzer

## 入力

`<候補技術> <対象リポジトリ> [--guidelines <パス[,パス...]>]`

`--guidelines` はカンマ区切りのローカルファイルパスを受け取る。各パスの前後の空白を除き、相対パスは呼び出し時のカレントディレクトリを基準に解決する。
指定時は作業の冒頭ですべての指定ファイルを読み、技術導入・移行の調査、評価と報告に適用する。操作の許可はユーザーの依頼と既存オプションに従う。
空のパス、読込失敗、解消できない指示の競合があれば、該当箇所と理由を示し、影響する作業を進める前にユーザーに確認する。

候補技術と対象リポジトリを受け取る。
解決したい課題、制約、チーム、期限は既知情報から整理し、結論を左右する不足だけ確認する。
コードや依存関係の変更は行わない。

## 調査

リポジトリの構成、技術スタック、ビルド、テスト、CI、規模、関連実装を確認する。
必要なら `scripts/repo-snapshot.sh` と `references/stack-detection.md` を参照する。
スクリプトは本Skillの位置を基準に解決する。

候補技術の公式資料から、対応環境、公開版、ライセンス、移行手順、制約を調べる。
保守状況、採用事例、代替技術は判断に必要な範囲で確認する。
URL、確認日、対象バージョンを記録する。

- 親が候補技術・対象リポジトリ・制約を確定する。上位指示が許し、読み取り向けサブエージェントを利用できる場合は、両側に独立した実質的な調査があれば、リポジトリの実態と候補技術の公式資料を別々に調査開始時点で並列に委譲する。単独でも大量の読み取りが必要なら委譲する。短い調査や先行結果に依存する読み取りは親が直接行う。例えば、現在版に依存する移行情報は、版が判明してから確認する。
- 子には目的、重複しない担当範囲、対象パス・版（固定している場合はSHA）、適用される規約と `--guidelines` の関連部分を渡す。編集・テスト実行・投稿・環境変更は行わせず、判断材料、`path:line` や一次資料のURL・確認日・対象版、未確認事項だけを返させる。
- 親は必要な結果を待ち、失敗や部分結果を区別し、重複と矛盾を解消する。結論を左右する根拠を原典で確認し、現状と候補の要件を照合して5軸評価と推奨を決める。委譲できなければ直接調べ、委譲できなかった範囲を明示する。

## 評価

次の5軸を、このコードベース固有の根拠で評価する。

1. 技術的互換性: ランタイム、依存、ビルド、既存フレームワーク、テスト。
2. 移行コスト: 対象範囲、段階移行、自動化、CI変更、工数と前提。
3. 効果: 性能、開発体験、保守、エコシステム、安全性。
4. リスク: 破壊的変更、学習、撤回可能性、保守、費用、成熟度。
5. 必要性: 課題の実在、費用対効果、現行技術での解決、機会費用。

他社事例の性能値を、そのまま対象リポジトリの予測値にしない。
不明な費用や効果は不明として残す。
導入を正当化するために根拠を水増ししない。

## 報告

推奨・条件付き推奨・現時点では非推奨を、理由とともに先に示す。
直後に5軸の評価をMarkdown表で置き、評価軸・判断・対象リポジトリでの根拠を対応付ける。複数案を扱う場合は、同じ5軸で比較する。
「判断」は軸ごとに基準をそろえる。例えば互換性は「対応」「条件付き対応」「非対応」とし、判断に必要な根拠が足りない項目は「不明」とする。

リポジトリと候補技術の前提、最小導入案または現行維持案、未確認事項を続ける。
構成を変える導入案では既存構成と候補技術の接点を、段階移行案では工程の順序と各段階の前提を、案の説明に `mermaid` コードブロックで図示する。図には現行と提案の区別が分かるラベルを付け、判断を左右する点を一文で添える。
`flowchart` では、日本語や括弧を含むノードラベルを `A["設定(任意)"]` のように二重引用符で囲む。
重要な事実には出典を対応付ける。

取得失敗があっても、独立して確認できる調査を続ける。
未取得の最新情報を記憶で補って確定しない。
