# Agent Creator

## 入力と成果物

エージェント名または用途の説明を受け取り、Claude CodeのAgentファイルを作成する。
目的、発火条件、権限、動作、完了条件、エラー時の扱いを自己完結した形で記載する。

## 手順

1. 会話と既存構成から、目的、具体的な利用場面、期待動作、編集権限、配置先を整理する。既知情報を再質問せず、設計を大きく左右する不足だけ確認する。利用例の件数は固定しない。
2. `references/subagent-vs-skill.md` を読み、隔離された役割・権限・コンテキストが必要か判断する。Skillが適切なら理由と設計案を示す。ユーザーがAgentを明示指定している場合は、形式変更を勝手に行わない。
3. `references/agent-template.md` を参照し、用途に必要な設定を選ぶ。利用可能なフィールド・値が不明な場合は、対象環境または公式仕様で確認する。
4. 指定配置先を優先する。未指定なら既存の配置規約から選び、ユーザースコープとプロジェクトスコープの選択が重要な場合だけ確認する。
5. 既存ファイルを読む。ユーザー変更を保持し、必要なAgentファイルを作成する。
6. frontmatter、参照先、権限、完了条件、正常・対象外の利用例との整合性を静的検証し、不備を修正する。
7. 配置先、役割、使用例、検証結果を報告する。

## 設計基準

- nameはkebab-caseとし、descriptionには役割と使用条件を書く。自動選択を誘うだけの定型句は加えない。
- tools・disallowedTools・permissionModeは最小権限で設計する。`bypassPermissions` を安易に採用しない。
- modelはユーザー指定と対象環境に従う。memory、isolation、maxTurns、skills、hooks、mcpServers、backgroundは必要な場合だけ検討する。
- メモリを使う場合はスコープと参照・更新条件を明記する。
- 並行編集では所有範囲や隔離方法を定める。実行制限は必要な仕事を途中終了させない値にする。
- hooksを設定する場合は、参照先の存在と処理内容を確認する。
- 詳細な例は参照資料へ置き、rootには実行時に必要な判断と制約を残す。

## 検証の境界

生成したAgentを自動起動して実作業を行わせない。
静的検証と実行検証を区別し、実際の発火・ツール制限・異常系を未検証ならその旨を報告する。
実行テストを依頼された場合は、対象と副作用を確認した範囲で行う。

## エラー

ファイル不在は周辺を探索し、権限や対象が解決できない場合は必要な情報を示す。
通常の生成不備は自分で修正して再検証する。
