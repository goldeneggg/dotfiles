# Issue Decomposer

## 引数

```text
[作成内容の説明] [--type github|linear] [--project 名前または参照] [--status ステータス名] [--auto] [--dry-run] [--guidelines <パス[,パス...]>]
```

| オプション | 動作 |
|---|---|
| `--type github\|linear` | 起票先を指定する。省略時は依頼文に従い、指定がなければGitHubを使う |
| `--project` | GitHubではProjectの名前またはURL、Linearではteamの名前またはキーを指定する |
| `--status` | GitHubではProjectのStatus、Linearではteamのワークフローステータスを指定する |
| `--auto` | 内容を提示し、作成の許可が明確でない場合も承認を待たずに作成する |
| `--dry-run` | 全Issueの本文ファイルとメタデータ案の作成までで止め、Issueは作成しない |

`--guidelines` はカンマ区切りのローカルファイルパスを受け取る。各パスの前後の空白を除き、相対パスは呼び出し時のカレントディレクトリを基準に解決する。作業の冒頭ですべて読み、解決済みの絶対パスを後続のIssue作成にも引き継ぐ。空のパス、読込失敗、解消できない指示の競合があれば、影響する作業を進める前に確認する。

作成内容の説明がなければ会話の文脈から対象を特定する。特定できない場合だけ確認する。日本語で進め、Issueの言語は対象リポジトリの既存Issueの慣習に従う。

## 1. Issue作成の共通規則を適用する

作業の冒頭で [issue-creator](../issue-creator/SKILL.md) を全文読み、作成先と内容の調査、重複確認、本文とメタデータの作成、操作許可、起票、作成後の検証、途中失敗からの再開に関する規則を適用する。本Skillは分解と順序付けだけを追加し、起票処理を再実装しない。

指定された `--type`、`--project`、`--status`、`--auto`、`--dry-run`、`--guidelines` はissue-creatorへ引き継ぐ。projectとstatusなどのメタデータは、親Issueとすべてのsub-issueへ共通適用する。既存の親Issueを指定する `--parent` は受け取らず、タスク全体を表す親Issueを新しく作る。

## 2. 親Issueとsub-issueへ分解する

親Issueにはタスク全体の目的、対象範囲、守るべき制約、全体としての完了条件を書く。sub-issueの本文を親へ複製せず、親子関係は作成先のネイティブ機能で表す。

sub-issueは2件以上とし、次の基準をすべて満たす最小の成果単位へ分ける。

- 一つの明確な責務と、第三者が判定できる完了条件を持つ。
- 先行する依存Issueが完了した後なら、単独のPRとしてレビュー・マージできる。
- 単独でリリースしても、既知の壊れた状態や不自然な中間状態を残さない。
- その成果に不可欠な実装、テスト、文書更新は同じIssueに含める。

調査・実装・テストなどの工程、変更ファイル、担当者の違いだけでは分けない。独立した成果にならない小項目を先回りしてIssue化せず、同じ成果を完成させる作業はまとめる。

この基準でsub-issueを2件以上作れない場合は何も起票しない。分割できない理由と、単一Issueのタイトル・目的・やること・完了条件の案を示し、issue-creatorでの作成を案内して終了する。

## 3. 着手順序と依存関係を決める

親子構造は親Issueとその直接のsub-issueからなる一階層に限定し、孫Issueは作らない。各sub-issueについて、開始前に完了している必要がある他のsub-issueだけを依存先とする。単なる推奨順序を依存関係として登録せず、依存しないIssueは同じ着手グループで並行実施可能とする。親Issue自体はsub-issueの依存先にしない。

依存関係は循環のない有向グラフにする。循環が生じる場合は責務を統合または再分割して解消し、依存元が先になるトポロジカル順に並べる。タイトルには通し番号や独自IDを付けない。

作成前の一括提示では、親Issueのタイトルと、全sub-issueの着手グループ・タイトル・依存先・単独成果を表で示す。依存関係が分岐・合流する場合は、issue-creatorの図示規則にも従う。本文には関係を文章で重複させず、GitHubではsub-issueとblocked by / blocking、Linearではparentとblocks / blocked byのrelationを使う。

## 4. 一括作成して検証する

確定した親Issue、sub-issue、依存グラフと共通オプションを一つの作成要求としてissue-creatorへ渡す。issue-creatorによる全タイトル・本文・メタデータの提示を今回の一括プレビューとし、同じ内容を重ねて提示したり定例の承認を追加したりしない。

Issue作成が明示されていれば、解消が必要な曖昧さや重複がない限り提示後に続行する。親Issueを最初に作成し、sub-issueをトポロジカル順に作成して、作成済みのIssue参照で親子関係と依存関係を設定する。`--dry-run` では外部作成を行わず、全Issueの本文ファイルとメタデータ案を報告して終了する。

作成後はissue-creatorの規則に従って全Issueを取得し直し、タイトル、本文、共通メタデータ、親子関係、依存関係を確認する。途中で失敗した場合は作成済みIssueを保持し、重複作成を避けて未作成分または未完了の設定だけを再開する。
