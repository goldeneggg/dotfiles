# レビュー評価基準

レビューでは以下の5観点をすべて適用する。変更内容に応じて重点は調整してよいが、観点自体は省略しない。

## コード品質

- 変更が新しいバグや問題を導入していないか
- エラーハンドリングが適切か
- コードが読みやすく保守しやすいか
- 命名とコード構成が意図を正確に表しているか
- 同じレイヤーやモジュールの周辺コードを読み、ファイル・クラスの責務分割、依存関係の向きと注入方法、API・データ表現、状態管理、エラー処理、例外・エラーの型、命名などの実装パターンと一貫しているか
- ログのレベル、出力条件、メッセージ形式が周辺コードの運用設計と整合しているか。既存パターンから逸脱する場合は、要件や不具合修正などの合理的な理由があるか

## コーディング規約

- プロジェクトの `CLAUDE.md` に記載された規約へ準拠しているか
- コードのフォーマットと構造が適切か
- インポート順序がプロジェクトまたは言語の規約に従っているか
- 変更した振る舞いに対応するテストと、既存のテストパターンとの整合性があるか
- テストが変更・削除・無効化されている場合、仕様または実装の正当な変更に対応しているか。期待仕様が変わっていないのに、失敗していたアサーション、境界値、異常系、回帰テストを弱めたり失ったりしていないか。CIを通過させること自体は、テスト変更の正当化根拠としない
- アサーションの削除・緩和、`skip` や対象絞り込み、入力値の都合のよい置換、実装結果を固定的に返すモック、スナップショットの一括更新などにより、テストが本来検出すべき不具合を見逃す状態になっていないか。意図は推測せず、仕様・実装・テストの差分から確認できる事実で判断する

## セキュリティ

- 潜在的な脆弱性を導入していないか
- 秘密情報や認証情報をハードコードしていないか
- 信頼境界に応じた入力バリデーションがあるか
- セキュリティ上重要な処理で、暗号ライブラリや認証・認可の仕組みを正しく使用しているか

## ベストプラクティス

- 言語やフレームワークの公式な推奨事項に準拠しているか
- 並行処理がある場合、競合・キャンセル・終了処理を考慮しているか
- エラーハンドリングとログ出力が運用上有用か
- リソースの取得と解放が対になっているか

## デグレ（リグレッション）と影響範囲

変更箇所だけでなく、diff 外の既存コードまで読み取り、変更が既存の振る舞いを意図せず壊していないか確認する。

- **影響範囲の調査**: 変更・削除された関数、メソッド、API、型、公開定数、設定キーを内容検索し、diff 外の呼び出し元が変更後の仕様に追従しているか
- **後方互換性と契約**: シグネチャ、例外・エラー種別、デフォルト値、副作用、公開インターフェースに破壊的変更がないか
- **説明にない挙動変化**: outline または PR 説明にない振る舞いの変更が混入していないか
- **失われた責務**: 削除・変更されたロジックが担っていたバリデーション、フォールバック、エッジケース処理が抜け落ちていないか

`--blind` では outline と PR 説明を取得しないため、「説明にない挙動変化」とは判定しない。代わりに、diff と既存コードから観測できる挙動変化・影響範囲・安全確認できない点を列挙し、変更の意図や正当性は推測しない。

必要に応じて最新の公式仕様を調べ、プロジェクト固有のガイドラインと併せて判断する。

## 重要度

- 🔴 **Critical**: セキュリティ脆弱性、データ損失、本番環境への重大な影響。マージ前の修正が必須
- 🟠 **High**: 再現可能または可能性の高いバグ、重大な規約違反、明確な性能劣化。マージ前の修正を強く推奨
- 🟡 **Medium**: 正しさを直ちに損なわない改善、リファクタリング、軽微な規約違反。マージ可能だが改善候補
- 🟢 **Low**: コメント、命名、スタイルなど任意対応の改善

重要度は問題が起きる条件と影響に基づいて判定する。問題の種類だけで機械的に決めない。

## PR承認判断

- ✅ **承認可能**: Critical 0件かつ High 2件以下
- ⚠️ **条件付きで承認可能**: High 3〜5件。内容と条件を明示して判断する
- ❌ **要修正**: Critical 1件以上または High 6件以上
