# 指摘の記述指針

問題点と改善点を重要度別に整理し、各指摘に以下をすべて含める。項目を埋められない場合は、根拠が不足していないか再確認する。

- **指摘**: 現在の実装で何が起きるか
- **指摘理由**: 問題が起きる条件、仕組み、コード上の根拠
- **本来あるべき姿**: 期待される動作または満たすべき条件
- **ユーザーへの影響**: 利用者または運用者が、どの操作でどのような不利益を受けるか。直接的な影響がない場合は、保守や将来の不具合への間接的な影響
- **修正案**: 問題を解消する具体的な方法
- **該当箇所**: diff 内のファイルパスを `path/to/file.ext:42` 形式で記載
- **根拠資料**: 判断に用いた公式文書などがある場合のみ記載

## 文章の書き方

- 一般的で意味が明確な言葉を使い、独自の造語・比喩・略し方を作らない
- 専門用語や略語は、対象コードや公式文書で使われている場合に限って使う。一般的でない語は最初に短く説明する
- 一文では一つの論点だけを扱い、主語・条件・結果を省略しない
- 「適切に処理する」「考慮が必要」のような曖昧な表現で終わらせず、必要な動作を具体的に書く
- 抽象的な名詞を重ねず、「誰が」「どの操作をすると」「何が起きるか」を動詞で説明する

「指摘理由」ではコードの状態を言い換えるだけでなく、その状態が問題を起こす仕組みを説明する。「ユーザーへの影響」は推測で補わず、確認できた範囲と未確認の範囲を区別する。
