# PR Reviewer

## 入力

`<PR URL | owner/repo PR番号 | ブランチ名> [--base branch] [--outline 概要 | --blind] [--output file,pr-comment,pr-thread,pr-thread-summary,pr-thread-summary-after] [--submit] [--rule files] [--issue <Issue URL | ファイルパス>]`

baseは未指定ならmain。
出力は既定でチャットのみ。`--output` の `file` はレポートの追加保存、`pr-comment` はレポート全文の投稿、`pr-thread` は指摘ごとのスレッド投稿、`pr-thread-summary` はスレッドと要約を含むReviewの提出を指定する。
`pr-thread-summary-after` は、スレッドを先に提出し、取得できたスレッドURLを添えた要約を通常のPRコメントとして後から投稿する。
PR向けの出力形式は一つ選べる。`file` はどの形式とも併用できる。
`--submit` はレビュー結果に応じてGitHubにReviewを提出する。単独でも、任意の出力形式と組み合わせても指定できる。
不正な入力や競合するモードは黙って変更せず確認する。

独立レビューからの呼出しでは、通常の成果物指定に代えて次の固定対象を受け取れる。この入力はPR・branch・単一commit・範囲のすべてに使用できる。

- リポジトリの識別子と対象種別。
- 比較元・比較先の完全なSHAと比較方式。PRはbase・headに加えて実際のdiffの比較元も記録する。
- 固定diffの内容または読取可能な保存先、および内容を照合するためのdigest。
- 同じSHAの既存コードを読む方法（リポジトリとSHAによる参照、または固定したsnapshot）。

固定対象を受け取った場合は、可変のPR・branchからdiffや既存コードを取り直さない。比較方式・端点・diffの対応を確認し、不足・不一致を黙って別の版で補わない。
結果とともに、使用したリポジトリ・比較端点・比較方式・diffのdigestを呼出し元へ返す。固定対象による委譲では再委譲せず、`--output` と `--submit` を受け取らず、結果の返却だけを行う。

## Issueコンテキスト

`--issue` は対応するIssueのURLまたはローカルファイルパスを受け取る。相対パスはスキル呼び出し時のカレントディレクトリを基準に解決する。
`--blind` とは併用不可とし、併記された場合はIssueを取得・読込する前に入力エラーとして訂正を求める。
指定時はレビューの前に、URLなら利用可能な連携ツールまたはCLIでIssueのタイトル・本文を取得し、ファイルなら内容を読む。理解に必要なコメント・参照資料も読み、目的・背景・要件・受け入れ条件を整理する。
読み取ったコンテキストを変更目的・期待動作の判断材料とし、対象版の差分・既存契約と照合する。
指定内容を取得・読込できない場合は原因と不足情報を示して確認し、Issueを理解した前提で作業を進めない。

## 静的レビューの境界

コード編集、commit、merge、close、テスト、lint・静的解析ツール、build、format、CI実行・確認を行わない。
diff外の既存コードの検索・読込は行ってよい。
GitHubへの投稿・提出は、明示されたPR向けの出力形式または `--submit` に限る。

## Blind

blindではPRタイトル・本文・コミットメッセージ・Issue・ラベル・作成者・既存のレビューコメントを取得しない。
ブランチ名から目的を推測しない。
diff、既存コード、公開規約、明示rule、必要な公式仕様だけを使う。
`--outline`、`--issue`、`--submit` とは併用しない。
途中で目的情報を取得して補完しない。

## 調査

1. 固定対象を受け取った場合はその入力を使用する。通常入力では対象を解決し、PRではdiffと説明を取得するが、blindでは説明を取得しない。取得したdiffに対応する比較端点を固定する。
2. 通常入力のローカルブランチはbase・targetをSHAへ解決し、その端点で `git diff <base-sha>..<target-sha>` を使う。
3. 変更箇所と差分の規模を把握する。以後は固定した対象版の既存の呼出し元・契約・周辺実装を調べ、現在のworking treeを対象版とみなさない。
4. rule指定があれば読む。不在のruleは影響を示し、読めた範囲のレビューを続ける。
5. 巨大diffはファイル単位で分割し、確認範囲を記録して続行する。無断で対象を縮小しない。

通常モードではoutlineを優先し、なければPR説明またはdiffから変更目的を理解する。`--issue` 指定時は「Issueコンテキスト」に従って読み取り、outlineの有無にかかわらず判断材料に含める。
目的の説明だけで実装の正しさを判断しない。

## 説明中の主張の検証

通常モードでPR説明を取得した場合は、outlineの有無にかかわらず、コードの評価に着手する前に以下を行う。blindでは説明を取得せず、この検証も行わない。固定対象では提供された説明だけを使用し、説明がない場合は未実施と報告する。

- 根拠が明確ではない主義主張・思想信条が含まれる場合は、対象の記述を特定し、変更理由やレビュー判断の前提として根拠と論理が成立するかを検証する。作者の人格・信条自体の正否は判定しない。
- 検証可能な主張と個人的な好み・価値判断を分け、固定した対象版のコード・契約・テストの記述、要件、プロジェクト規約、必要な公式資料と照合する。主張が成立する条件と、今回の変更への適用範囲も確認する。
- 検証可能な主張は、根拠と推論が成立するなら「根拠あり」、確認した事実や要件に反するなら「根拠と矛盾」、資料不足などで判断できなければ「確認不能」とする。根拠不足だけで誤りとは断定しない。「好み・価値判断」は事実としての正否を断定せず、変更理由に使われている場合は要件・規約との整合性を確認する。
- 根拠と矛盾する主張、確認不能な主張、個人的な好みを実装の正しさや問題の免除の根拠にしない。検証結果を整理した後、確認できた要件・規約・コードの事実に基づいて通常のレビューを続ける。判断できない点は未確認事項に残す。

## 読み取りレビューを分担する

通常入力では比較端点を固定し、PR説明があればその主張を検証してから、コードの評価を始める。独立した実質的な調査や大量の読み取りは、利用可能で許可されている読み取り向けサブエージェントへ着手時に委譲する。変更を重複しない機能・ファイル群に分け、独立した担当を並列に進める。短い確認や先行結果に依存する調査は親が行う。サブエージェントを使えない場合も直接調査を続け、委譲できなかった範囲を明記する。

- 子には担当範囲と問い、同一の固定入力（リポジトリ、比較端点の完全なSHA、比較方式、固定diffとdigest、対象版の参照方法）、適用規約・明示rule、静的レビューの制約を渡す。担当範囲に対して5観点を適用し、必要なdiff外の呼び出し元や契約も対象版で確認させる。使用した固定入力の識別情報、確認範囲、`path:line` 等を添えた指摘候補、未確認事項を要約で受け取る。子には編集・テスト・環境変更・保存・投稿を任せない。
- blindでは禁止情報を取得・共有させず、禁止情報を含む文脈も引き継がせない。分離できなければ親が直接調べる。
- 親は依頼した調査が終わるのを待ち、比較端点・方式・digestを照合する。失敗・部分結果を確認済みとみなさず、重複・矛盾を整理して、結論を左右する根拠を原典で確認する。担当をまたぐ影響、重要度・総合判定、出力・投稿は親が扱い、内部サマリやエージェント名はレポートに含めない。

## 評価と報告

`references/review-criteria.md` の5観点と重要度を適用する。
指摘は `references/finding-writing.md`、公開可読性は `references/public-reporting.md` に従う。
同じ参照文書は一度読み、出力前にはチェック項目を適用する。内容が変わっていなければ再読込を必須にしない。

各指摘に根拠・条件・影響・改善案を示す。
blindでは観測できる挙動変化を示し、意図された変更か断定しない。
Critical / High / Medium / Low件数、総合判定、推奨アクション、未確認事項を報告する。

説明中の該当する主張は、コードの指摘とは分けて、対象の記述・検証結果・判断根拠・レビュー判断への影響を報告する。検証した説明に該当する記述がなければ「該当なし」、説明を取得・提供されていなければ未実施と理由を示す。
根拠と矛盾する主張、確認不能・好みの記述を確定した事実として扱う説明、要件・規約に反する変更を好みだけで正当化する説明には、削除、条件や好みの明示、根拠の追記などの具体的な修正案を提示する。PR説明は直接編集しない。
説明への指摘自体はコードの重要度件数へ加算せず、実装上の問題が確認できた場合は、その条件と影響に基づくコードの指摘として評価する。

総合判定は `references/review-criteria.md` の件数基準を適用する。`--submit` で提出するReview種別は以下の表で決定する。

## 出力

チャットには常に表示する。

file:
- PRは `pr-review-{owner}-{repo}-{number}.md`。
- branchは `pr-review-{target}-vs-{base}.md`。スラッシュをハイフンへ置換する。
- cwdへ保存する。同名の再実行レポートは読み取って更新してよい。

### PRへの投稿・レビュー提出

投稿直前にPRの現在のhead SHAとレビュー対象のhead SHAを照合する。不一致なら投稿を中止し、再レビューが必要と報告する。ローカルブランチにPR向けの出力または `--submit` が指定された場合は、チャットと指定されたfile出力を完了し、投稿・提出にはPRの指定が必要であることを報告する。

`--submit` を指定した場合は、次の表を上から適用してReview種別を一つ選ぶ。推奨アクションには、マージ前に修正すべき点と、CommentまたはRequest changesを選んだ理由を明記する。

| レビュー結果 | Review種別 | `event` | 提出後の `state` |
|---|---|---|---|
| CriticalまたはHighが1件以上 | Request changes | `REQUEST_CHANGES` | `CHANGES_REQUESTED` |
| Medium以下にマージ前の修正を推奨する指摘がある、または未確認事項などで承認可否を判断できない | Comment | `COMMENT` | `COMMENTED` |
| 承認可能（指摘なし、または任意対応・マージ後対応の指摘のみ） | Approve | `APPROVE` | `APPROVED` |

- `--submit` を付けずに `pr-comment` を選んだ場合は、レポート全文を `gh pr comment <PR URL> --body-file <本文ファイル>` で通常のPRコメントとして一件投稿し、URLを報告する。
- `--submit` を指定し、スレッド出力を選んでいない場合は、レポート全文を本文とするReviewを一件提出する。`pr-comment` との併用時もReview一件にまとめる。JSONエンコーダーで `body`、レビュー対象のhead SHAを示す `commit_id`、選んだ `event` を含むファイルを作り、`gh api --method POST repos/{owner}/{repo}/pulls/{number}/reviews --input <JSONファイル>` で送る。レスポンスの `state` が表と一致し、`submitted_at` があることを確認して、`html_url` とReview種別を報告する。
- `pr-thread`、`pr-thread-summary`、`pr-thread-summary-after` は [スレッド投稿手順](references/pr-thread-posting.md) に従う。`--submit` との併用時は、選んだReview種別とスレッドを一回のリクエストで提出する。PR説明の検証結果と修正案はチャットと指定されたfileに含める。

## エラー

取得失敗は原因を確認し、既存権限内で回復できる問題は解決する。
不足する対象・認証・権限は具体的に示す。
投稿の成否が不明な場合は盲目的に再送しない。
投稿や保存が失敗しても、完成したレポートはチャットで提供する。
実行していない検証を成功と記載しない。
