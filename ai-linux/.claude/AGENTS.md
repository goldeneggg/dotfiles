# Personal Rules

## 作業ルール

### 情報収集と編集

- ファイルの読込・探索・内容検索は、利用可能なら組み込みツールを優先する。
- 読込範囲は調査目的とツールの出力上限に合わせる。必要なら行数やサイズを確認し、関連箇所を検索して分割する。
- 全文確認が必要な対象は、出力を切り詰めずEOFまで読む。省略された出力を読込済みと扱わない。
- 編集・上書き前に、同一セッションで対象ファイルを読む。読込後に更新された可能性がある場合は再読込し、既存のユーザー変更を保持する。
- Bash実行時はコマンド名に `\` を付け、意図しないエイリアス参照を避ける。連結した各コマンドにも適用する。説明文やコード例には付けない。

<!-- 要確認: コマンド名のバックスラッシュ必須は、個人環境の運用方針として現状維持。 -->

### CLIツール

- ファイル名検索は、利用可能なら `fd` または `rg --files` を使う。
- 内容検索は、利用可能なら `rg` を使う。
- `rg` のOR検索には `|` または複数の `-e` を使う。

### Code Mode のツール実行

Code Modeで `functions.exec` を利用できる場合、同じ段階にある独立した呼出しは一つのexec内で並列実行する。

- 部分結果も有用なら `await Promise.allSettled([...])` を使い、全結果を確認する。
- 一つの失敗で全体を中止すべき場合は `await Promise.all([...])` を使う。
- 依存関係のある操作、待機・再開、承認、競合する更新、結果に応じて次を選ぶ調査は順次実行する。

### 依頼範囲と完了

- 依頼された内容に集中し、「ついで」の修正や無関係なリファクタリングを行わない。
- フォールバックは基本的に追加しない。必要性がある場合は、ユーザーが判断できる形で提案する。
- 明示された作成・修正依頼は、対象内の実装と「テストと検証」の範囲の検証まで進める。同じ作業の許可を繰り返し求めない。
- 仕様・対象・権限が大きく変わる場合、または未承認の破壊的・不可逆操作が必要な場合は、その操作に必要な判断を確認する。
- 確認が必要でも、既に許可された独立作業は進める。承認を求める場合は、可能な準備を終え、具体的な差分・送信内容・影響を提示する。
- スキルの手順が明示されたユーザー指示と競合する場合は、上位指示とユーザー指示を優先する。
- 未実施の検証や残作業を明示し、未確認の状態を完了と報告しない。

### エラーとトラブルシューティング

- エラーメッセージと関連するローカルの実装・設定を確認し、原因を裏付けてから修正する。
- 仕様やバージョン差が判断に影響する場合は、公式ドキュメントを確認する。
- 原因を変えずに同じ操作を繰り返さない。
- 既存の権限・依頼範囲で安全に回復できる問題は修正して続行する。権限拡張や要件変更が必要な場合は、原因・影響・必要な判断を報告する。

## コーディングルール

### 基本

- 短さより可読性を優先し、意図が明確な変数名・関数名を使う。
- 意味を持つマジックナンバーは定数化する。
- エラーは早期にチェックし、適切に早期リターンする。
- エラーメッセージには、何が・なぜ失敗したかを書く。必要に応じてログを追加する。
- コメントは非自明な前提や「なぜ」を説明する。自明な処理の説明は加えない。

### 簡潔さとYAGNI

- 現在の要件を満たす最小の変更を実装する。将来の拡張、設定項目、抽象化、汎用化は、要件または既存の利用箇所が必要とする場合だけ追加する。
- 単一用途のヘルパー・インターフェース・ラッパーを先回りで作らない。再利用される場合、複雑な境界を隠す場合、名前が呼出し側を明確に読みやすくする場合だけ抽出する。
- 同等の機能を新設する前に、既存の関数・ユーティリティ・パターンを探して再利用する。

### 異常系とエッジケース

- 信頼できない値（ユーザー入力、外部API、ファイル、環境変数など）は、それを受け取る境界で一度だけ検証する。型・スキーマ・コンストラクタ・呼出し元で保証済みの値を防御的に再検証しない。
- 発生条件を具体的に説明できない失敗に対して、分岐・nullチェック・try/catch・リトライ・タイムアウトを追加しない。
- 例外は、その場で回復・変換・文脈付与できる場合だけ捕捉する。握りつぶしたり、ログだけ出して処理を続けたりしない。
- 投機的または極めて稀な競合・セキュリティ・障害ケースのために複雑さを加える前に、具体的な失敗シナリオ、発生可能性、複雑さのコストをユーザーに示して合意を得る。理論上の堅牢性のために黙って範囲を広げない。

### テストと検証

- 検証の量は変更の規模とリスクに合わせる。まず変更箇所に関係する既存のテスト・lint・型チェック・ビルドを実行する。
- 新しいテストは、依頼された場合、またはリポジトリの規約や既存テストの構成から当然期待される場合だけ追加する。
- テストは公開された振る舞いを検証する。実装ロジックをテストに複製しない。モックは外部依存の分離に必要な場合に限る。
- 同じ振る舞いを重複して検証するケースや、言語・ライブラリ・フレームワーク自体の動作を確かめるテストを書かない。
- 既存のテストやコマンドで確認できる場合、検証用の独自スクリプトを作らない。一時的なデバッグコードやログは成果物に残さない。

## 応答ルール

- 結論を最初に述べ、説明は必要最小限にする。
- 並列な項目や手順には箇条書きを使い、コード例は短く実用的にする。
- 見出しは必要な場合だけ使い、h2・h3を基本とする。
- 段落は短く、一つの話題を扱う。リストは5項目以内を目安にするが、必要な情報を省略しない。
- 冗長な前置き、重複、過度な丁寧語、独自の造語、不要な例外説明を避ける。
- URLを応答に含める場合は、URL文字列そのものを使う。anchor形式にしない
  - URLをanchor形式で応答しても、URLの正当性をユーザーが視認出来ないし、ターミナルで作業しているユーザーはそれをクリックできず、メリットが何も無い
- ユーザーへの報告および承認依頼は、調査・分析を統合した自己完結型の応答を優先する。
  - 最も重要な要件は、ユーザーが過去のメッセージをスクロールして読み返さなくても、最新の応答だけで判断できることである
- ユーザーへの質問、選択肢の提示、承認依頼では、質問だけを単独で提示してはならない。質問の直前に、以下の判断材料をまとめて提示する。過去の応答で説明済みであっても、承認判断に必要な情報は必ず再掲する。
    1. 調査で判明した事実
    2. 問題の原因
    3. 検討した修正方針
    4. 選択肢ごとのメリット・デメリット
    5. 変更対象ファイルと影響範囲
    6. 推奨案とその根拠
    7. ユーザーに判断してほしい内容
