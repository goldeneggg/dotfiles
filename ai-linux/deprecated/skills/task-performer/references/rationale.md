# task-performer ルール背景（Rationale）

SKILL.md 本文と詳細手順から参照される、各ルールの詳細な背景説明。本文側は「ルール＋1行要約」に留め、背景や判断根拠を確認したいときにこのファイルを参照する。毎回読む必要はない。

## タスク管理コンテキストをリポジトリ成果物に残さない

**対象**: コードコメント・コミットログの両方。

**残してはいけない情報**:

- タスクドキュメントのファイルパス・URL（例: `docs/tasks/todos/001-setup/README.md`、ローカル/イントラのタスク管理URL）
- タスクID・TODO番号への言及（例: 「TODO-123対応」「タスク001の要件で追加」「YYYYMMDD-{name} プロジェクト」）
- セッション内の作業ログパス（例: `logs/NNN-{task}/...`）や、当該リポジトリ外の個人専用ディレクトリ（`.claude/agent-memory/` 等）への参照

**Why**: コードコメントとコミットログは、ソース／`git log` の一部としてリポジトリに永続化され、変更経緯を追う第三者（将来の自分・新規参画者・OSS閲覧者を含む）が読む。タスクドキュメントやタスクIDは対応者のローカル環境にしか存在せず、読み手は参照できない。残しても「どこを見ればよいか」という誤った期待を生むだけで、混乱の原因になる。コメント・コミットログは、コードとリポジトリ内の情報だけで自己完結させる。

**代わりに書くべき内容**: 「なぜ」その実装・変更にしたか（設計判断の理由・トレードオフ・非自明な前提や注意点）と、変更内容の要約（what）・リポジトリ内のファイルパスや関連機能名など、リポジトリだけを見て理解できる情報。タスク管理側の文脈は、Phase 7 の作業結果レビュー・気づきメモ・`PROGRESS.md` に留める。

## テストの軽量/重い分類とローカル実行方針

**Why**: 重いテスト（DB・外部API・コンテナ起動を伴う integration/E2E）はローカルで実行環境（DB・コンテナ・認証情報・ネットワーク）の準備が必要で、環境差異による偽陽性・偽陰性が起きやすく、実行コストも高い。これらはCIの統一環境で実行する方が再現性・信頼性が高い。一方、軽量ユニットテストは環境非依存で高速なため、ローカルで即座に回す方がフィードバックループが短く有益。だからこそ「軽いものはローカル、重いものはCI」と役割を分ける。

## フォールバック実装の禁止

**Why**: フォールバックはエラーを静かに隠蔽し、バグの発見を遅らせる温床となる。またタスク要件に書かれていない挙動を勝手に追加すると、どこまでが仕様なのかが曖昧化し、後続の変更時に「その挙動が仕様なのか偶然なのか」が判断不能になる。

## スコープ外の改善は「気づきメモ」として別途報告

**Why**: スコープ外の変更は計画レビューで合意していないため、ユーザーは意図を把握できずレビューコストが跳ね上がる。また関係のない変更が同一コミットに混ざるとrevertやcherry-pickが困難になり、git履歴の価値が損なわれる。

## シンプルさ優先、拡張性は次点

**Why**: 要件外の汎用性は「想像上の未来」のために今コストを払う行為で、多くの場合その未来は来ない。読み手・レビュワーが理解すべき情報量を最小化することが、長期的な保守性・可読性に直結する。

## task-starterプロジェクトの自動認識と読込方式の選択

**Why**: task-starter プロジェクトは複数ファイルを横断して読むため、既定では読み取りと要約を専門エージェントに切り出し、本体のコンテキスト消費を抑える。

## 既定で過去ログを読まない理由

**Why**: 多くのタスクでは標準ファイル群と進捗正本の `PROGRESS.md` だけで計画立案できる。`logs/` はコミットログ・調査メモ・コマンド出力・試行記録などが蓄積するため、不足を確認した場合だけ `--with-log` で追加取得する。

## git add 前にpre-commitの整形処理を実行する理由

**Why**: `git add` → `git commit` の順で進めると、コミット時にpre-commit hookが整形を行っても、その整形結果はステージング後の変更として扱われるため、コミット完了後に整形差分が作業ツリーに再発生してしまう。`git add` の前に整形処理を完了させておくことで、ステージング内容とコミット内容と作業ツリーの内容を一致させ、コミット後の差分再発生を防ぐ。

## PR説明の整合性チェック

**Why**: PR修正を重ねると当初の説明が実態と乖離し、レビュワーが古い説明を前提にレビューしてしまう。実装完了時に説明を同期させることで、レビュー品質と情報の鮮度を維持する。
