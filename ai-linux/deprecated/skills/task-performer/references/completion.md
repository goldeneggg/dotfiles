# 承認後の後処理

Phase 8の開始前に「Phase 8: 承認後の処理」を読む。PR修正作業の場合は最後に「PR説明の整合性チェック」も読む。オプション・権限・共通ルールは [SKILL.md](../SKILL.md) に従い、共有保存契約は [task-management-contract.md](../../_shared/references/task-management-contract.md) を適用する。追加タスクの文書作成・提示前確認には [document-writing-guide.md](../../_shared/references/document-writing-guide.md) も適用する。

## Phase 8: 承認後の処理

承認されたら以下を実施する。`--auto` 指定時は、通常実装ではPhase 7で全 `AC-ID` が `充足`、WIPでは実行したLint・ビルドに失敗がないことを承認相当として扱う:

1. **pre-commitフックによる事前整形**（`git add` 実行前に必ず行う）
   - `.git/hooks/pre-commit` と `.githooks/pre-commit` の存在を確認する
   - いずれかが存在する場合、`git add` より前にフックへ処理を委ねず、フックスクリプトの中身を確認したうえでそこに定義されている処理（フォーマッタ・Lintコマンド等）を直接実行する
   - `--wip`指定時にフックがテストを含む場合、テストコマンドは事前に直接実行せず、フォーマッタ・Lintだけを分離して実行する。安全に分離できなければフック全体の事前実行を省略し、commit時の自動実行に任せる。自動実行されたテストを抑止せず、結果をWIPの検証状況へ記録する
   - 実行結果がエラーの場合: エラー内容を確認 → 修正 → 再実行を繰り返し、エラーが無くなるまで完了としない（3回修正しても解決しない場合はユーザーに報告し、続行/中断を確認。[SKILL.md](../SKILL.md) の「エラーハンドリング」参照）
   - 実行結果がOKになったら（または両ファイルとも存在しない場合はそのまま）、手順2へ進む

2. **git管理されている変更ファイルのステージング**
   ```bash
   git add {変更したファイル}
   ```
   対象は実装で変更したコード・テスト等のみ。タスクドキュメント（`todos/`・`progresses/`・`logs/` 配下等、手順4で更新するファイル）は、それがgit管理下にあっても`git add`/`git commit`の対象に含めない（下記手順4参照）。
3. **コミットログファイルの出力**
   - "commit-{`date +'%Y%m%d%H%M%S'` コマンドの実行結果}-{title}.txt" というファイル名でファイルに書き出す（`git commit -F` で使用）
   - 出力先: task-starterプロジェクトの場合は `logs/NNN-{task}/` 配下。それ以外は推奨案を含む複数の選択肢を提示してユーザーに確認。`--auto` 指定時はリポジトリルートへ出力する
   - 形式:
     ```
     {Conventional Commits形式のメッセージ}

     {作業内容の詳細をmarkdown形式で記載}
     {1行72文字以内}
     ```

   **コミットログにタスク管理コンテキストを残さない**: タスクドキュメントのパス、タスクID・TODO番号、作業ログパス（`logs/NNN-{task}/...`）、リポジトリ外の個人専用ディレクトリ（`.claude/agent-memory/` 等）への参照は含めない。代わりに変更の目的（why）・内容の要約（what）・リポジトリ内のファイルパスや機能名など、リポジトリだけで理解できる情報を書く。タスク管理側の文脈は Phase 7 の作業結果レビューや気づきメモ、`PROGRESS.md` に留める。背景の詳細は [rationale.md](rationale.md) を参照。

   **commitを含むオプション指定時のコミット実行**: `--commit`・`--commit-push`・`--commit-push-pr` のいずれかを認識していた場合、ステージ済み差分にタスク外の変更が含まれないことを確認し、出力したコミットログファイルを使って以下を実行する。
   ```bash
   git commit -F {出力したコミットログファイルのパス}
   ```
   オプション未指定の場合はログファイル出力に留め、コミットは実行しない。コミット実行後はハッシュを記録する。コミット対象の差分がない場合は空コミットを作らず、その旨を記録して指定された後続操作の要否を確認する。

   **push・PR作成**:
   - `--commit-push`・`--commit-push-pr` では、送信先remote・branchと未pushコミット全体を確認して提示し、確定した対象へ通常のpushを行う。今回のタスク外のコミットが含まれ、送信が許可されているか不明な場合は確認する。必要ならupstreamを設定し、送信済みなら再pushは不要。
   - `--commit-push-pr` では [pr-creator](../../pr-creator/SKILL.md) の手順でタイトル・本文を準備して提示し、push成功後にPRを作成する。既存PRのstateとhead/base（リポジトリ・ブランチ）を照合し、一致するOpen PRがある場合はURLを報告して新規作成を省略する。Closed/Mergedの履歴だけでは作成を止めない。既存PRの照会失敗を「PRなし」と扱わない。既にpush済みであることと、許可された実行範囲を `pr-creator` に引き継ぐ。
   - `--wip`との併用時は、`pr-creator`へ`--draft`と、PRタイトルの先頭に`[WIP] `を付ける形式指定を渡す。タイトルに同じprefixを重複させず、作成後にDraft状態とタイトルを確認する
   - commit失敗時はpushへ、push失敗時はPR作成へ進まない。通信エラーで成否が不明ならリモートの状態を確認してから再試行を判断する。force pushや別remoteへの切り替えを自動で行わない。
   - コミットハッシュ・push先・PR URL（作成/既存）を報告する。失敗・保留があれば未完了の操作を明記し、進捗正本にも残作業・ブロッカーとして反映する。指定操作が未完了のままタスク全体を完了扱いにしない。

4. **進捗正本の更新**（task-starter形式のファイルパスで提供された場合）
   - 指定されたTODOタスクファイルには進捗を書き戻さない。旧形式のチェックボックスも更新しない。依頼に含まれる定義変更は [SKILL.md](../SKILL.md) の Phase 4-3 と共有保存契約に従う
   - `progresses/NNN-{task}/PROGRESS.md` の全 `AC-ID` を Phase 7 の判定と根拠で更新する。TODOに存在しないID、重複ID、欠落IDがあれば完了にせず修正する
   - `--wip`を指定せず、全 `AC-ID` が `充足` で承認済み（`--auto` では承認相当）の場合だけ、状態を `完了` に更新し、最終更新・完了した作業・残作業・ブロッカー・成果を共有契約の必須形式に揃える
   - `--wip`指定時は状態を`完了`にせず`進行中`のままにし、完了・未完了の`W-ID`、実装済みの大枠、意図的な未実装部分、次に必要な作業、全`AC-ID`の判定と根拠を更新する
   - 個別正本の更新直後に同期スクリプトを実行し、`progresses/README.md` の該当行が個別正本と同じ状態・最終更新を示すことを確認する。個別正本と一覧の更新を同じ処理として扱う
   - 旧形式では `PROGRESS.md` の既存形式を維持して状態と成果を更新し、TODOのチェックボックスは読み取り専用として扱う。移行は別途提案し、自動実行しない
   - `progresses/NNN-{task}/` には `PROGRESS.md` 以外を出力しない。コミットログ・レビュー結果・テスト成果物・調査メモ・コマンド出力・試行記録は `logs/NNN-{task}/` に置く
5. **追加・申し送りタスクの起票**（Phase 7 で承認された場合のみ）
   - **`1xx` 番台**で連番フォルダを作成（既存の最大 `1xx` 番号 +1。最初は `101`）
   - task-starterプロジェクトの場合: `todos/1xx-{kebab-name}/README.md` を `task-starter` の todo-template 形式（フロントマター + 開発原則チェック含む）で作成し、`depends_on` に当該タスクIDを設定。文書の作成と提示前の確認は [SKILL.md](../SKILL.md) の Phase 4-3 の共有の執筆ガイドに従う
   - 同じIDの `progresses/1xx-{kebab-name}/PROGRESS.md` と `logs/1xx-{kebab-name}/` を作成し、残作業を全 `W-ID`、受け入れ条件の検証を全 `AC-ID: 未確認` として進捗正本を `未着手` で初期化する
   - 起票した個別正本を作成後、同期スクリプトを実行して `progresses/README.md` に新しい `1xx` 行を追加する
   - `todos/README.md`（ロードマップ）が存在すれば、タスク一覧表の末尾に 1xx タスクを追記
   - task-starterプロジェクトでない場合: 起票先・形式を推奨案を含む複数の選択肢を提示してユーザーに確認
6. **PR説明の整合性チェックと更新**（PR修正作業の場合のみ。「PR説明の整合性チェック」参照）

## PR説明の整合性チェック

PR修正作業（既存PRに対するレビュー指摘対応・バグ修正・機能追加など）の場合、Phase 8 の最終ステップとして対象PRの説明が実装と乖離していないかを検証し、必要に応じて更新する。

**対象判定**: 以下のいずれかに該当する場合にこのステップを実行する:
- タスク指示にPR番号・PR URLが含まれている
- タスク指示が「PRのレビュー指摘対応」「PRの修正」など既存PRへの作業であることが明示されている
- 作業対象ブランチに紐づくオープンなPRが存在する（`gh pr view` で確認）

**手順:**

1. **現在のPR説明を取得**
   ```bash
   gh pr view {PR番号} --json body,title --jq '.title + "\n---\n" + .body'
   ```
2. **実装内容との整合性を確認**
   - PR説明（タイトル・本文）が、今回の修正を含めた最終的な実装内容を正しく反映しているか確認
   - チェック観点:
     - タイトルがPRの最終的な目的を正しく表しているか
     - 変更内容のサマリが実態と一致しているか
     - 削除・変更された機能が説明に残っていないか
     - 新たに追加した機能・変更が説明に反映されているか
     - テスト計画が実態と合っているか
3. **乖離がある場合 — PR説明を更新**
   - 乖離を検出したら、更新内容をユーザーに提示して承認を得る
   - 承認後、`gh pr edit` で更新:
     ```bash
     gh pr edit {PR番号} --title "{新タイトル}" --body "{新本文}"
     ```
   - 更新はPR説明の「同期」であり、体裁の好みによる書き換えは行わない。既存の書式・構成は尊重し、実装と乖離している部分のみ修正する
4. **乖離がない場合** — 「PR説明は実装と整合しています」と報告して完了
